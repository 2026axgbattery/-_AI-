# MVP 구현 실행 계획서

**작성 기준**: `prd.md`(2026-09-10 개정, 2단 캐스케이드 반영) 및 관련 산출물(`.docs/02~04`, `domain-constants.md`, `correlation-reliability-review.md`)
**작성일**: 2026-09-10
**목적**: 실제 코드 작성 착수 전, `prd.md` 요구사항을 무엇을·어떻게·언제까지·무엇을 완료 기준으로 구현할지 한 문서로 정리한다. 이 문서는 새 내용을 만들지 않고 이미 확정된 `.docs/`·`prd.md` 산출물을 실행 관점에서 다시 엮는다.

## 1. 배경 및 동기

- 저장소에는 현재 기획 산출물(PRD, 아키텍처, DB 스키마, Day별 실행계획)만 있고 애플리케이션 코드는 아직 없다(`CLAUDE.md` "저장소 현재 상태" 참조).
- 전역 규칙(`~/.claude/CLAUDE.md` Work Process)에 따라 실질적인 코드 작성에 들어가기 전 계획서를 먼저 작성해야 하며, 이 문서가 그 역할을 한다.
- `prd.md`는 2026-09-10 개정으로 **X(공정인자)→Y(잔존율/포화도 proxy)→Z(20시간 용량) 2단 캐스케이드** 구조로 확정됐고, 같은 날 기술 스택도 "Streamlit MVP → v2 Next.js/FastAPI 전환" 계획을 건너뛰고 **MVP부터 Next.js(화면)+FastAPI(분석 엔진)+SQLite**로 피벗했다. 이미 `.docs/02_nextjs-fastapi-구현-아키텍처.md`, `.docs/03_sqlite-스키마-설계.md`, `.docs/phase/phase_01~03_plan.md`가 이 피벗을 반영해 작성돼 있으므로, 본 계획서는 **그 문서들을 대체하지 않고 실행 순서·완료 기준 관점에서 통합 인덱스** 역할을 한다.
- 3일 집체 PBL이라는 시간 제약이 명확하므로, "무엇을 만들지"보다 "3일 안에 종단간(E2E)으로 동작시키는 순서"가 이 계획서의 핵심 가치다.

### 2.2 제외 (Non-goals, `prd.md` §3)

- train/val 분리·R²/RMSE 정식 검증, 재학습 파이프라인 정식화
- 캐스케이드 vs 베이스라인 **정량** 비교(구조만 MVP, 수치 비교는 v2)
- `saturation_calc`(실제 포화도) 활성화 — 공극 상수 확보 자체가 불투명(스트레치 목표로도 가정 금지, `domain-constants.md`)
- 외부 클라우드 API/LLM 연동, 사용자 인증/권한 체계, 다중 동시 편집 서버 인프라

### 2.3 범위 판단 원칙

- `prd.md` §10 Open Questions 중 **해결됨** 항목(1~5)은 그대로 구현 전제로 삼는다.
- **여전히 확인 필요**(6~18) 항목은 구현을 막지 않되, 화면에 "참고용/검증 전" 표기, 설정 가능한 임계값(하드코딩 금지)으로 처리한다 — 특히 SPEC 하한값(#11), 형명별 최소 표본 n(#16), 도메인 상수 0.336g/Ah(#7·§6-③ 공통 단서)는 더미 수치를 그대로 하드코딩하지 않는다.

## 3. 방법

### 3.1 기술 스택 및 아키텍처

`.docs/02_nextjs-fastapi-구현-아키텍처.md`, `.docs/04_기술-스택-정의서.md` 그대로 따른다.

- 프런트: Next.js(App Router) — `output/*.html` 5개 목업을 화면 단위로 이식, `design.md` 세방 CI 토큰 픽셀 단위 적용
- 백엔드: FastAPI — `analysis/`(회귀·VIF·유의성·진단·추이, UI/웹 프레임워크 비의존 순수 Python) + `routers/` + `db/`
- DB: SQLite 단일 파일, `.docs/03_sqlite-스키마-설계.md` DDL을 `backend/db/schema.sql`로 그대로 사용, append-only
- 로컬 전용: FastAPI는 `127.0.0.1` 바인딩, 외부 네트워크 호출 없음(사외반출 금지 데이터 원칙)

### 3.2 실행 순서 (Day 1~3)

상세 작업 항목·완료 기준은 `.docs/phase/phase_01_plan.md`~`phase_03_plan.md`에 이미 확정돼 있다. 이 계획서에서는 각 Day의 목표만 요약한다.

- **Day 1** — 프로젝트 초기 셋업(Next.js+FastAPI 헬스체크 연동 우선 검증) → DB 스키마 적용 → 업로드·매칭(①) → 수기입력(②) → `LotDerived` 파생값 계산까지 종단간 1회 동작.
- **Day 2** — 1단(X→Y) 회귀+VIF+p-value(③-1) → 2단(X+Y→Z) 회귀 + 베이스라인(③-2) → 형명별 상세 분석(③-3) → Y 추이 그래프(③-4).
- **Day 3** — 미매칭 로트 Y·Z 일괄 예측(④-1·④-2) → SPEC 판정 + 원인진단(⑤) → 종단간(①~⑤) 오류 없는 1회 이상 실행 점검 → 디자인 토큰 마감.

각 Day 종료 시 **다음 Day로 넘어가기 전에** 전역 규칙의 사전/사후 점검(의도-방법 일치, 부작용 여부, 목적 부합, 다른 기능 영향)과 개발 후 점검(빌드/린트/타입체크/테스트)을 수행하고 결과를 보고한다. 코드 규모상 자동화 테스트가 아직 없다면 그 사실을 명시한다.

### 3.3 핵심 설계 원칙 (구현 시 반드시 준수)

- 1단 X셋은 `process_data.csv` 컬럼만 사용, `fill_weight`/`water_loss`는 X에서 제외(완전공선 방지), `charge_ratio` 등 무차원 비율로 정규화(§6-③-1).
- 2단 학습은 반드시 **실측 Y**로 하고, 추론 시에만 Ŷ를 투입 + `input_y_source` 플래그 구분(§6-③-2).
- 1단/2단 모델의 "최근 학습 시점"을 화면에 분리 표시(`AnalysisRun.is_latest_for_stage`, stage별 갱신 주기 차이 반영).
- 회귀계수 크기와 함께 p-value/유의성을 표시해 노이즈성 상관을 걸러낸다(`correlation-reliability-review.md` 방식 그대로: 피어슨 r + p-value, 유의수준 0.05).
- 형명별 분석은 표본 부족(중앙값 2~3건) 시 "표본 부족 — 참고용"으로 전환하는 설정 가능한 임계값을 둔다.
- UI는 `design.md` 세방 CI 토큰(§6 CSS Custom Properties)을 그대로 사용하고, 오렌지·그린 동시 강조 금지 등 금지사항(§7)을 지킨다.

## 4. 완료 기준 (`prd.md` §9 성공 지표 그대로 채택)

- ①~⑤ 파이프라인이 실제(더미) 데이터로 **종단간 오류 없이 1회 이상 실행**됨.
- 시험 미매칭 41개 로트의 **Y·Z 산출률 100%**.
- **X→Y→Z 캐스케이드**와 **X→Z 베이스라인**이 구조적으로 둘 다 구현됨(정량 비교는 v2).
- `water_loss_residual` 기반 이상 로트가 상대 순위로 1건 이상 검출됨(절대값 해석은 보류).
- 동일 입력에 대해 원인진단 결과가 100% 재현 가능(규칙 기반).
- `AnalysisRun`에 stage 구분과 함께 이력이 누락 없이 기록됨.
- Day별 완료 기준은 `.docs/phase/phase_01~03_plan.md`의 세부 체크리스트를 따른다.
