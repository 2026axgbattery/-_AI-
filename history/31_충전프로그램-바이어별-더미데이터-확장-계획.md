# 31. 충전 프로그램 바이어별 더미 데이터 확장 계획

## 배경/동기

사용자가 "★ 260428 AGM CF 충전 프로그램 3.xlsx"에 있는 바이어들을 기반으로 더미 데이터를 만들어 기존 더미 데이터에 새롭게(추가로) 반영해달라고 요청했다.

현재 데모 DB(`backend/db/app.db`)의 `Lot`에는 6개 용량군(50/60/70/80/90/105Ah) 전체에 걸쳐 바이어 코드 **H/K/S** 3종만 존재한다(원본 100행 참조 데이터 + `AGM60_S1`/`AGM70_S1` 더미 확장분). 반면 `backend/etl/charge_program.py`로 이 엑셀을 파싱하면 아래처럼 훨씬 다양한 바이어 코드가 나온다(`is_variant`만 다른 중복 제외, "All"은 90/105Ah 전용 — 이미 모든 바이어 코드에 폴백으로 매칭되므로 제외):

| 정격용량 | 스펙에 있는 바이어 코드 | 이미 Lot에 있음(H/K/S) | 이번에 추가할 바이어 |
|---|---|---|---|
| 50Ah | H, Y | H | **Y** |
| 60Ah | B, S, D, Y, Z, C, G, H, V | H, S | **B, D, Y, Z, C, G, V** |
| 70Ah | B, S, H, Y, Z, C, D, G | H, S | **B, Y, Z, C, D, G** |
| 80Ah | B, S, D, H, Y, Z, C | H, S | **B, D, Y, Z, C** |
| 90/105Ah | All | (K도 All로 매칭됨) | 없음(이미 전부 매칭됨) |

총 **19개 신규 (정격용량, 바이어) 조합**을 새 `model_name`(`AGM{용량}_{바이어}1` 형식, 기존 `H1`/`S1` 접미 관례와 동일)으로 추가한다.

## 범위

- 신규 스크립트 `scripts/generate_charge_buyer_dummy.py` 작성 — `scripts/generate_agm60_70_dummy.py`(`.docs/26` 재설계 버전)와 동일한 접근(공정 데이터 CSV 전체 풀에서 공정조건 공통분포 샘플링 + 용량군별 fill_weight/cell_weight_mean + 실측 검증된 X→Y/X→Z/CCA 방향·크기를 수식+노이즈로 반영)을 재사용하되, 대상 `model_name`을 위 19개 신규 조합으로 일반화한다.
- 규모는 기존 5,000행/모델 규모가 아니라 **모델당 공정데이터 60행(월 5행×12개월) + 시험 샘플 20건**(`history/21` 최초 버전과 동일한 소규모)으로 가볍게 유지한다 — 이번 목적은 통계적 검정력 확보가 아니라 "충전 프로그램 바이어 커버리지 확장·매칭 확인"이므로 대규모 재현이 불필요하다.
- `charge_amount`는 **기존 관례(=`charge_ratio`(공정 조건 공통분포, 정격용량 대비 약 100~125%) 기반 소규모 스케일)를 그대로 따른다** — 별도로 기록해 둔 "charge_amount가 충전 프로그램 Total 충전량[Ah]과 스케일이 다르다"는 이슈(`충전량_이탈도_점검.xlsx` 참조)를 이번 작업에서 임의로 재정의하지 않는다. 즉 신규 로트도 기존 로트와 동일하게 `charge_program_deviation_pct`가 구조적으로 큰 음수(~-80%)로 나올 수 있으며, 이는 이미 알려진 별도 이슈로 남겨둔다(스케일 자체를 바꾸는 것은 기존 회귀·문서 수치에 영향을 미치는 별도 결정 사항).
- 산출물(`충전프로그램_바이어_더미_process.csv`, `충전프로그램_바이어_더미_test.xlsx`)을 실행 중인 데모 백엔드(8000번 포트)의 `POST /api/upload/process`·`POST /api/upload/test`로 반영한다(append-only이므로 기존 데이터 삭제 없음). 검증 전용 DB(`app_test.db`)는 이번 요청 범위 밖이라 건드리지 않는다.
- 반영 후 `ChargeProgramSpec` 매칭이 실제로 붙는지(각 신규 바이어 조합의 `charge_program_deviation_pct`가 NULL이 아님) 확인한다.
- `CLAUDE.md`·`.docs/07`에 이력 기록.

## 방법

1. `backend.etl.charge_program.parse_charge_program_workbook`로 엑셀을 파싱해 (정격용량, 바이어) 조합을 구하고, 기존 H/K/S·"All"을 제외한 19개 신규 조합을 코드로 도출(하드코딩 대신 파싱 결과 기반 — 향후 엑셀이 바뀌어도 스크립트가 스스로 갱신됨).
2. `generate_agm60_70_dummy.py`의 통계 로직(공정조건 pooled stats, 용량군별 fill_weight/cell_weight_mean, Y/Z/CCA 드라이버)을 재사용해 19개 신규 모델 각각에 대해 공정데이터 60행 + 시험 샘플 20건을 생성.
3. lot_id에 바이어 코드를 포함해 유일성 보장.
4. 8000번 포트 데모 백엔드로 업로드 API 호출 → 반영 확인(`SELECT` 몇 건으로 매칭 여부 점검).
5. 문서 갱신(`CLAUDE.md`, `.docs/07`) 후 이 계획서를 `history/`로 이동.

## 완료 기준

- 19개 신규 (용량, 바이어) 조합이 `Lot`에 존재하고, 각각 `charge_program_deviation_pct`가 NULL이 아닌 값으로 계산됨(= `ChargeProgramSpec` 매칭 성공).
- 기존 Lot/ProcessData/TestData는 그대로 유지(삭제·수정 없음, append만 발생).
- `pytest tests/backend`·`ruff check backend` 통과(백엔드 코드 변경 없으므로 회귀 없어야 함).
