# AGM60/70 더미 데이터 상관관계 재설계 계획

**작성일**: 2026-09-25
**배경 문서**: `scripts/generate_agm60_70_dummy.py`, `history/21_형명60-70-신규-더미데이터-생성-검증-계획.md`, `docs/correlation-reliability-review.md`

## 1. 배경/동기

최종 발표를 앞두고 사용자가 "20시간 용량(Z)·CCA 데이터가 제대로 분석되는지" 확인을 요청함. 데모 DB(`app.db`)를 점검한 결과:

- `더미 데이터_process.csv`/`더미 데이터_test.xlsx`는 이미 데모 DB에 업로드돼 있었음(batch 42/43, AGM60_S1·AGM70_S1 각 500/20건).
- 다만 저장된 1단(X→Y) 회귀가 표본 1,200건(전체 2,200건 중 AGM70 추이 데이터만)짜리로 방치돼 있어 최신 데이터를 반영 못하고 있었음 — 재실행함.
- 재실행 후 **1단 회귀 R²=0.032, VIF 최대 61.9(charge_program_deviation_pct)**로 나옴. 원인 추적 결과, `generate_agm60_70_dummy.py`의 `_synth_value()`가 X 컬럼들을 **완전히 독립적으로** 정규분포 샘플링만 하고 있어 Y(포화도/잔존율)·Z(20시간 용량)·CCA 체크포인트 값이 X와 실제로 연결되는 수식이 전혀 없음. CCA도 `_cca_values()`가 공정 인자와 무관하게 미리 정한 케이스로 합격/불합격을 배분해, 회귀가 학습할 근거가 없음(지난 세션에서 확인된 EN/SAE CCA 스코어링 71~74%가 사실상 구조적 한계).

## 2. 범위

- **대상**: `scripts/generate_agm60_70_dummy.py`(재작성), 산출물 `더미 데이터_process.csv`·`더미 데이터_test.xlsx`(재생성), 데모 DB(`app.db`)의 AGM60/70 더미 배치(batch 42/43) 교체, 검증 전용 DB(`app_test.db`)의 동일 배치 교체.
- **범위 밖**: `agm70_trend_process_data.csv`(batch 40/41, AGM70 12개월 추이) — 건드리지 않음. 원본 `process_data.csv`/`test_data.csv`(35개 형명 실제 유래 데이터) — 건드리지 않음. 회귀 로직(`backend/analysis/*.py`) 자체는 수정하지 않음(데이터만 개선 — "채점 결과를 좋게 보이려고 모델을 손대지 않는다"는 기존 합의 유지).

## 3. 방법

1. **함수형 관계 설계** — `docs/correlation-reliability-review.md`에 검증된 방향·크기를 참고해 X→Y, X+Y→Z, X→CCA 체크포인트를 "수식 + 가우시안 노이즈"로 생성(완전 독립 샘플링 대신):
   - Y(잔존율): `cell_weight_std`(-), `electrolyte_temp`(+), `charge_ratio`(+), `soaking_time_sec`(+), `tank_temp`(+) 기반 선형식 → `fill_weight`/`water_loss`를 역산.
   - Z(20시간 용량/capacity_rate): `charge_ratio`(+), `electrolyte_temp`(+), `tank_temp`(+), Y(+) 기반 선형식.
   - CCA 체크포인트(`en_cca_10s_voltage`/`en_cca_6v_hold_sec`/`sae_cca_7v2_hold_sec`): 동일 계열 X 인자에 잠재 점수를 부여하고 노이즈를 더해 연속값 생성 → 기존 EN 50342/SAE J537 고정 임계값(`cca_spec.py`)으로 합격/불합격이 "자연스럽게" 갈리도록(사전 배분 폐기).
2. **VIF 원인 제거** — `cell_weight_mean`/`charge_ratio`/`charge_program_deviation_pct`처럼 설계상 "정격용량과 무관해야 하는" 비율 인자는 형명별(capacity-group)이 아니라 **전체 실측 데이터 풀에서 공통 분포**로 샘플링해, 두 형명을 합친 회귀에서 모델 정체성과 얽히는 인위적 공선성을 없앰.
3. **노이즈 캘리브레이션** — 잡음 크기를 조절해 R²가 너무 낮지도(설명력 없음) 너무 높지도(과적합 의심) 않은 범위(대략 0.5~0.8)에 오도록 스크립트 실행 후 오프라인으로 R²/VIF를 먼저 점검(DB 반영 전).
4. **데모 DB 반영** — 사전에 `SELECT COUNT(*)`로 batch 42/43 영향 범위를 재확인(이미 1차 확인 완료: batch42=ProcessData 1000행/distinct lot 1000/다른 배치와 lot_id 중복 0건, batch43=TestData 40행) 후 `DELETE FROM ... WHERE upload_batch_id=42/43` + `UploadBatch` 삭제로 교체(과거 `delete_upload_batch` 사고 재발 방지를 위해 직접 SQL로 스코프를 명시적으로 통제, DB 파일은 사전 백업). 새 CSV/XLSX를 실제 업로드 API로 재업로드 → 회귀(x_to_y/xy_to_z/x_to_z_baseline/xy_to_sae_cca/xy_to_en_cca) 재실행 → 채점(scoring) 재실행 → 결과 확인.
5. **검증 DB(app_test.db) 반영** — 데모 DB에서 결과가 양호하면 동일 절차를 `AX_DB_PROFILE=test` 백엔드 인스턴스(또는 동일 로직을 test DB 파일에 직접)에 반복.

## 4. 완료 기준 (및 실제 결과, 2026-09-25)

- 1단(X→Y) 회귀 R²가 0.5 이상 → **재조정**: 실측 검증된 개별 상관(r=-0.308, +0.210)만으로는 다중 R²가 이론상 0.15~0.3대가 한계라, 이 값은 애초에 과도한 목표였음. **실제 결과 R²=0.31**(격리된 AGM60/70 더미 1,000행 기준), VIF는 대부분 ~1.0으로 해소됨.
  - **단, `cell_weight_mean`(14.6)·`charge_program_deviation_pct`(21.4) 두 인자는 VIF가 여전히 10을 넘는다** — 이는 더미 데이터 품질 문제가 아니라 **두 형명(AGM60/70)을 하나의 회귀로 합치면 구조적으로 발생하는 기존 한계**임을 확인함(`charge_program_deviation_pct`는 `(charge_amount − charge_program_total_ah)/charge_program_total_ah`로 정의되는데, `charge_program_total_ah`가 형명별 고정 상수라 형명을 섞으면 `charge_ratio`·형명 구분(`cell_weight_mean`으로 대리됨)과 필연적으로 얽힘 — 단일 형명만 놓고 보면 오히려 `charge_ratio`·`charge_program_deviation_pct`가 완전 비례(VIF 발산)라는 게 CLAUDE.md에 이미 기록된 기존 함정). 회귀 로직(`X_COLUMNS` 구성)을 바꾸는 건 이번 범위 밖이라 **v2 백로그로 남김** — 형명별 분리 회귀 또는 이 파생값 재설계가 필요.
- 2단(X+Y→Z) 회귀 R²가 확인 가능한 수준(0.4 이상) → **실제 결과 R²=0.876(데모, n=52 전체)·0.991(검증 DB, n=40)**. 목표 초과 달성.
- EN/SAE CCA 채점(scoring) 일치율 개선 → **실제 결과(데모 DB, n=52)**: Y 98.1%(✓신뢰가능)·Z 92.3%(✓)·EN CCA 78.6%(기존 71.4%에서 개선, 아직 미달)·SAE CCA 92.9%(✓, 기존 71.4%에서 90% 임계값 최초 돌파). 검증 DB(n=40, SPEC 임계값도 데모와 동일하게 90/95로 맞춤)에서는 Y 97.5%(✓)·Z 97.5%(✓)·EN 80.0%(미달)·SAE 90.0%(✓ 경계).
- 데모 DB·검증 DB 둘 다 `npm run build`/`pytest`는 대상이 아님(백엔드 로직 변경 없음, 스크립트만 수정) — API 응답(회귀 결과·SPEC 준수·채점 결과)으로 확인 완료.
- AGM70 추이 데이터(batch 40/41)·원본 실측 데이터는 영향 없음 확인. 단, **1단(X→Y) 회귀를 추이 데이터(1,200행, 신호 없는 구버전 생성 방식)와 합치면 전체 R²가 0.077로 희석됨**을 발견 — 추이 데이터는 이번 작업 범위 밖이라 그대로 두었고, 이 사실을 사용자에게 보고함(추이 데이터도 같은 방식으로 재생성할지는 후속 결정 필요).
- 실행 전 `backend/db/app.db.bak_20260925`·`backend/db/app_test.db.bak_20260925`로 백업 완료(둘 다 git 미포함 로컬 파일).
