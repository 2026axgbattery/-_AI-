## 1. 문제 정의

창원 품질경영팀은 매월 전지 **포화도**(제품 성능과 직결되는 핵심 관리지표)를 관리하기 위해, 공정 데이터(설비 파라미터 등)와 시험 데이터(포화도, 성능 결과)를 각각 Excel로 취합한 뒤 **공정인자별로 개별 수작업 비교분석**을 수행하고 있다.

고통의 핵심은 세 가지다.

1. **복합 인자를 개별로만 본다** — 다수의 공정인자가 동시에 포화도에 영향을 주는데, 인자를 하나씩 떼어 보는 방식으로는 실제 영향 관계를 잡아내기 어렵다. 핵심 영향인자를 놓치거나, 어떤 인자를 먼저 관리해야 하는지(우선순위)가 담당자의 경험적 판단에 좌우된다.
2. **이력이 없다** — 분석 결과가 DB화되지 않아 매달 처음부터 다시 수작업을 반복한다. 담당자가 바뀌면 같은 기준으로 재현할 수 없고, 취합 과정에서 누락·불일치가 생겨도 추적할 수 없다.
3. **시험 전 로트는 깜깜이다** — 시험은 전수가 아닌 샘플로만 진행되므로, 시험을 거치지 않은 로트는 포화도도 제품성능(20시간 용량)도 사전에 알 방법이 없다.

**2단 캐스케이드가 이 세 번째 고통을 해소하는 방식**: 공정인자(X)만으로 포화도(Y)를 먼저 산출·예측하고, 이 X와 Y를 함께 입력해 제품성능(Z=20시간 용량)까지 연달아 예측한다. 즉 **시험을 한 번도 거치지 않은 로트도 X값만 있으면 Y·Z를 모두 얻을 수 있다** — 이것이 "포화도가 성능으로 이어지는 매개 지표"라는 이 과제의 핵심 가설이기도 하다.

결과적으로 **월 1회, 회당 10시간**이 데이터 취합~인자별 분석~결과 정리에 소요되며, 그 시간의 대부분이 재현 불가능한 수작업 비교에 쓰인다.

## 1-1. 핵심 용어 정의 (혼용 금지)

이번 개정에서 가장 중요한 변경점이다. 아래 3개 용어는 **서로 다른 개념**이며, 이 문서 전체에서 구분해서 사용한다.

| 용어 | 정의 | 산출식 | 산출 가능 범위 |
|---|---|---|---|
| **포화도 (saturation)** | 전해액이 셀 내부 총 공극(void) 부피 대비 얼마나 차 있는지의 비율 | `전해액 부피 / 총 공극 부피 × 100` (총 공극 = 세퍼레이터 공극(압착 상태 기준) + 극판 공극(화성 후 기준) + 자유 공간) | **공극 상수(모델별 세퍼레이터 사양·극판 공극률) 확보 시에만** 산출 가능 — 이번 더미 데이터에는 이 상수가 없음 |
| **잔존율 / 감액률 (retention rate)** | 전해액 주입량 대비, 감액(증발·유출 등)되고 남은 액량의 비율. 포화도의 **근사 대체 지표(proxy)**로 사용 | `(fill_weight − water_loss) / fill_weight × 100` | **전 로트(100개) 즉시 산출 가능** — `process_data.csv`만으로 계산됨 |
| **capacity_rate** | 시험에서 실측한 20시간율 방전용량이 정격용량 대비 얼마나 나왔는지의 비율 — 아래 §10-1에서 데이터로 확인한 결과 **Z(제품성능) 계열 지표**로 재분류됨 | `discharge_amount / rated_capacity × 100` (실측값과 오차 0에 가까움, §10-1 참조) | 시험 매칭 로트(59개)만 |

**이번 MVP의 잠정 결론(분기 B, 계산형)**: 공극 상수를 확보하지 못했으므로, **Y(포화도)는 잔존율(retention rate)로 근사**하고 `saturation_basis = 'proxy_retention'`, `saturation_source = 'derived'`로 화면·DB에 항상 병기한다. 이는 실제 포화도가 아니라 근사치임을 담당자·열람자가 항상 인지하도록 하기 위한 안전장치다(§7 참조, 단계별 실행 경로는 기획서 부록 "단계별 실행 경로" 참조).

**담당자 확인(§10-6 부분 해결)**: 실제 사내 "포화도" 관리 방식이 확인됨 — (1) 기준(basis)은 하나로 고정된 게 아니라 **사양(모델/스펙)마다 셀 전체 기준·세퍼레이터 기준을 각각 관리**한다. (2) 관리 타겟은 **계산형(이론치)**이지만 **실측도 병행**한다. 즉 `saturation_basis`('cell' | 'separator')와 `saturation_source`('measured' | 'derived') 두 필드를 이미 열거형으로 설계해둔 것이 실제 운영 방식과 일치한다 — **모델별로 이 두 값의 조합이 달라질 수 있다는 전제로 설계를 유지한다**(§7 `ConstantsByModel`/`LotDerived` 참조). 다만 **정확한 계산식(공극 부피 산출 방법)은 담당자도 정확히 모르며 설계 기밀일 가능성이 있다고 확인됨** — `saturation_calc` 실제 활성화는 "공극 상수를 나중에 확보하면 켠다"가 아니라 **"확보 자체가 불가능할 수 있는 스트레치 목표"**로 재평가해야 한다(`docs/domain-constants.md` 참조).

**capacity_rate는 더 이상 Y 후보가 아니다.** §10-1에서 확인했듯 `capacity_rate = discharge_amount / rated_capacity × 100`이 거의 정확히 성립하므로, capacity_rate는 "포화도"가 아니라 "정격 대비 방전용량 비율" — 즉 Z(20시간 용량)를 %로 표현한 값이다.

## 2. 타겟 사용자 + 페르소나

**주 사용자**: 창원 품질경영팀(분석 수행) + 생산기술팀 등 유관부서(결과 열람)

### 페르소나 1 — 김경준 (품질경영팀 주임, 분석 담당자·앱 운영자)
- 매월 공정/시험 CSV를 받아 직접 업로드하고, 수기 입력 2개 항목(§6-②)을 채워 넣는 실질적 운영자.
- 회귀분석 결과를 보고 핵심 인자를 판단해 보고서를 작성해야 하는 책임자.
- 데스크톱(로컬 PC)에서 작업하며, 데이터를 외부로 유출할 수 없는 제약 하에서 일함.
- 원하는 것: "업로드만 하면 인자별 영향도와 원인이 자동으로 정리되어, 내가 판단·보고에만 집중할 수 있으면 좋겠다."

### 페르소나 2 — 생산기술팀 대리 (결과 열람자)
- 본인 공정 조건이 포화도/성능에 어떤 영향을 주는지 확인하고 싶지만, 분석을 직접 수행하지는 않음.
- 데이터 입력·업로드 권한은 필요 없고, 대시보드와 원인진단 결과만 보면 됨.
- 원하는 것: "우리 라인 로트 중 부적합/저포화도가 나오면 원인이 뭔지 바로 알고 싶다."

## 3. 목표와 비목표

### Goals
- **X(공정인자)→Y(포화도)→Z(20시간 용량)의 2단 관계를 정량화**(회귀계수)하고, **X값만 입력하면 Y·Z를 연달아 산출**하는 파이프라인을 만든다.
- 월 10시간 소요되는 취합·분석 작업을 **2시간 이내(약 80% 단축)**로 줄인다.
- 분석 결과(1단·2단 계수, 베이스라인 비교)를 **이력으로 축적**(SQLite)한다.
- 시험을 거치지 않은 로트도 공정인자만으로 **Y와 Z를 일괄 산출/예측**한다.
- 부적합/저Y·저Z 로트에 대해 **원인 인자를 규칙 기반으로 자동 지목**하고 개선 권고를 제시해, 담당자가 바뀌어도 동일 기준으로 판단 가능하게 한다.
- 3일 집체 종료 시점까지 ①~⑤ 파이프라인(업로드→매칭→수기입력→1단/2단 분석→Y·Z 예측→판정/진단)이 **종단간 오류 없이 동작**한다.

### Non-goals (이번 3일 MVP 범위 아님 — 10월 여유 범위로 이관)
- 예측 모델의 학습/검증(train/val) 분리 및 R²·RMSE 등 성능지표 정식 검증
- 재학습(retraining) 파이프라인 정식화
- 캐스케이드(X→Y→Z) vs 베이스라인(X→Z) 비교의 **정량적 성능 검증** (구조는 MVP에 만들되, 수치 비교는 v2)
- 공극 상수 확보 후 실제 포화도(`saturation_calc`) 활성화 및 잔존율↔실제 포화도 회귀식 검증
- 실제 운영 데이터로의 최종 교체 검증
- 외부 클라우드 API/LLM 연동 (사외반출 금지 데이터이므로 전 구간 로컬 처리만 허용)
- 사용자 인증/권한 관리 체계 (역할 구분은 UI 레벨에서만, 계정 시스템은 범위 밖)
- 다중 동시 편집을 위한 서버 인프라 구축 (별도 배포 서버 없이 로컬 PC 웹앱)

## 4. 사용자 스토리

- 분석 담당자로서, 공정 CSV와 시험 CSV를 업로드하면 lot_id로 자동 매칭되길 원한다. 그래야 수작업 대조 없이 바로 분석에 들어갈 수 있다.
- 분석 담당자로서, 원본 데이터에 없는 항목(전해액온도·충전량·수조온도 등)을 로트별로 직접 입력하고 싶다. 그래야 회귀분석에 필요한 전체 인자셋을 완성할 수 있다.
- 분석 담당자로서, 공정인자와 포화도(Y) 간의 상관관계·회귀계수를 자동으로 계산해 보고 싶다. 그래야 어떤 인자가 얼마나, 어느 방향으로 영향을 주는지 즉시 파악할 수 있다.
- 분석 담당자로서, 포화도(Y)가 제품성능(Z, 20시간 용량)에 실제로 얼마나 영향을 주는지도 함께 확인하고 싶다. 그래야 포화도 관리가 성능 관리로 이어진다는 것을 수치로 설명할 수 있다.
- 분석 담당자로서, 매월 분석 결과가 자동으로 이력(DB)에 쌓이길 원한다. 그래야 다음 달에 처음부터 다시 하지 않고 추세를 비교할 수 있다.
- 분석 담당자로서, 시험을 거치지 않은 로트 전체에 대해 X값만으로 포화도와 성능을 일괄 예측하고 싶다. 그래야 시험 전에도 이상 가능성이 있는 로트를 미리 알 수 있다.
- 분석 담당자로서, 부적합/저포화도·저성능으로 판정된 로트에 대해 원인 인자가 자동으로 지목되길 원한다. 그래야 매번 인자를 하나씩 다시 뜯어보지 않아도 된다.
- 유관부서 열람자로서, 내 라인의 로트가 부적합 판정을 받으면 원인과 개선 권고를 바로 확인하고 싶다. 그래야 담당자에게 다시 문의하지 않고 대응할 수 있다.
- 후임 담당자로서, 전임자가 남긴 분석 이력과 판단 기준(회귀계수·SPEC 기준)을 그대로 이어받고 싶다. 그래야 담당자가 바뀌어도 같은 기준으로 관리를 지속할 수 있다.

## 6. MVP 기능별 상세 요구사항

**① 데이터 업로드 & 매칭**
- 공정 데이터 CSV, 시험 데이터 CSV를 각각 업로드받는다. **파일 선택(클릭)과 드래그앤드롭 두 방식을 모두 지원한다(2026-09-10 추가)**.
- 업로드가 끝나면 `lot_id`를 키로 두 데이터셋을 **자동으로** 조인한다 — 별도의 "매칭 실행" 버튼을 누를 필요가 없다.
- 시험은 전수가 아닌 샘플이므로 **미매칭 로트가 다수 발생하는 것을 정상 상태**로 처리하고, 매칭/미매칭 건수를 화면에 명시한다(에러로 취급하지 않음).
- 업로드 파일의 필수 컬럼(lot_id 포함)이 없으면 업로드를 막고 어떤 컬럼이 누락됐는지 표시한다.
- **(2026-09-10 개정) 매칭 결과가 표시된 뒤, 같은 화면 하단에 ② 수기입력(그룹 일괄 입력)을 바로 이어 붙인다.** 별도 페이지로 이동하지 않고 한 화면에서 업로드→매칭 확인→수기입력까지 끝낸다. 다만 **매칭이 끝났다고 1단·2단 회귀 분석까지 자동으로 실행되지는 않는다** — 분석 실행은 이 화면 하단의 명시적 버튼(§6-③ 진입)을 눌러야 시작된다.

**② 수기입력** (①과 같은 화면(`output/01_upload_matching.html`)에서 매칭 결과 바로 아래에 이어짐, 2026-09-10부터 별도 화면 아님)
- **수기입력(그룹 일괄 입력) 대상은 전해액온도(`electrolyte_temp`)·수조온도(`tank_temp`) 2개 항목이다.** (2026-09-10 개정 당시엔 충전량(`charge_amount`)도 포함해 3개였으나, **2026-09-21 사용자 결정으로 제외됨** — 형명·바이어별 충전 STEP 기준표(`ChargeProgramSpec`, §6-③, `history/19` Phase B)를 이미 확보해 그룹 추정치로 미입력을 채우는 이 경로가 더 이상 필요 없다고 판단. `charge_amount` 자체가 없는 로트는 여전히 1단·2단 회귀에서 자동 제외되지만, 안내 문구·그룹 일괄 입력 UI로는 더는 유도하지 않는다. `history/20_cca-en-sae-규격판정-대시보드-상세분석-반영-계획.md` 참조.) **MT(V)·MT(A)(`mt_voltage`, `mt_current`)는 수기입력 대상이 아니다** — `test_data.csv`(시험 데이터) 업로드 시 `lot_id` 매칭을 통해서만 자동으로 채워지는 값이며, 사람이 직접 입력하는 경로 자체를 두지 않는다. 시험을 거친 59개 로트에서만 값이 존재하고, 미매칭 41개 로트는 이 값 자체가 없는 것이 정상이다(§6-③, §10-5 참조). **이 화면에는 MT(V)/MT(A)를 노출하지 않는다(2026-09-10 재개정)** — 참고 배지로도 보여주지 않으며, 해당 값은 "시험 로트 한정 심층 분석"(§6-③-1) 화면에서만 다룬다.
- **더미 데이터 확인 결과**: 전해액온도·수조온도는 `process_data.csv`에 이미 포함되어 있어 이번 더미셋 기준으로는 수기입력이 거의 필요 없다. 다만 실제 운영 중 특정 달의 CSV에 이 컬럼이 비어 있는 경우를 대비해 아래 그룹 일괄 입력 방식을 설계한다.
- 화면은 다음을 지원한다: (1) 업로드된 CSV에 해당 컬럼이 존재하면 자동으로 값을 채워 보여준다. (2) 값이 비어 있는 로트는 **그룹 단위로 일괄 입력**할 수 있는 UI만 제공한다. **(2026-09-10 재개정) 로트별 개별 입력 UI는 화면에서 제외했다** — 그룹 일괄 입력이 이번 더미셋의 미입력 케이스(2건)를 모두 덮으므로 화면 단순화를 위해 제거했다. 그룹값과 다른 값이 필요한 예외 로트를 다루는 방법은 아직 정해지지 않았다(§10 오픈 이슈 참조).
- **그룹 일괄 입력 기준(신규, 담당자 요청 반영)**: 같은 형명(`model_name`)은 같은 화성 레시피·같은 수조 운용을 공유하는 로트 단위라는 현업 전제를 반영한다.
  - **전해액온도(`electrolyte_temp`)·수조온도(`tank_temp`)**: **형명(`model_name`) + 생산일자(`prod_date`) 조합**으로 그룹화한다. 같은 형명이 같은 날 같은 수조에 함께 투입돼 충전되므로, 형명만으로는 그룹이 너무 넓고(날짜가 다르면 다른 수조 배치) 생산일자까지 함께 묶어야 실제 배치 단위와 일치한다. 그룹을 선택(형명 선택 → 해당 형명의 생산일자 목록 표시 → 날짜 선택)하면 그 형명·그 날짜의 미입력 로트 목록이 미리보기로 나타나고, 값 하나를 입력해 일괄 반영한다.
  - (참고, 폐기됨) 이전엔 충전량(`charge_amount`)도 형명(`model_name`) 단위로 그룹화해 여기서 함께 입력했다. 형명 표기(예: `AGM105_S1`)의 접미 문자(S/H/K 등)가 "바이어(고객사)/스펙 구분 코드" 역할을 한다는 확인(아래 §10-19)은 여전히 유효하며 `ChargeProgramSpec`의 `buyer_code` 추출에 그대로 쓰인다.
  - 그룹 일괄 입력의 기본 동작은 "미입력 로트에만" 적용이다. **(2026-09-10 재개정) "이미 값이 있는 로트도 덮어쓰기" 체크박스를 선택하면 그룹 전체(이미 값이 있는 로트 포함)에 일괄 반영할 수 있다** — 이번 더미셋은 3개 항목이 애초에 결측이 없어 미입력 전용 모드로는 이 기능 자체를 시연·검증할 수 없다는 문제가 실사용 중 확인되어 추가함. 덮어쓰기를 선택하면 실수 방지를 위해 반영 대상 건수를 알려주는 확인 다이얼로그를 거친 뒤에만 반영된다.
- 미입력 항목이 남아있는 로트는(그룹 일괄 입력 후에도) 1단(X→Y) 분석 대상에서 제외하고 목록으로 안내한다.

**③-1 분석 대시보드 — X → Y (포화도) 회귀**
- **X(1단 입력)는 `process_data.csv` 컬럼만으로 구성한다.** 근거: MT(V)/MT(A)는 `test_data.csv` 전용 컬럼이라 미매칭 41개 로트에는 값 자체가 없다. 이걸 X에 포함하면 "④-1 미매칭 로트 Y 일괄 산출"이 애초에 불가능해져 성공지표의 "예측 커버리지 100%"도 달성할 수 없다. 따라서 MT(V)/MT(A)는 1단 X에서 제외하고, "시험 로트 한정 심층 분석"(59개 로트 대상 참고용 상관표)에서만 다룬다.
  - **담당자 확인(§10-5 해결됨)**: MT(V)/MT(A)는 공정 설정값이 아니라 **시험 단계에서 별도 측정하는 값**이다. MT(V)는 화성 후 전압(`voltage_2nd`, "완성전압")과의 차이를 보기 위한 것이고, MT(A)는 간이 CCA(저온시동전류) 측정으로 완성 용량의 상/하 방향성을 사전에 가늠하기 위한 것이다. 따라서 "시험 로트 한정 심층 분석"에는 `mt_voltage − voltage_2nd`(완성전압 대비 편차)와, 모델(정격용량)별로 정규화한 `mt_current`(간이 CCA 스크리닝)를 참고 지표로 포함한다.
- **1단 X셋 (물리적 인과 후보, `process_data.csv` 기준)**: `electrolyte_temp`, `tank_temp`, `soaking_time_sec`, `aging_days`, `formation_dv`(=`voltage_2nd − voltage_1st`), `cell_weight_mean`/`cell_weight_std`(6셀 중량 평균·표준편차), `charge_ratio`(=`charge_amount / rated_capacity × 100`), `charge_program_deviation_pct`(신규 2026-09-21, history/19 Phase B — 팀장 피드백 반영. 실제 총 충전량이 형명·바이어별 충전 STEP 프로그램의 Total 충전량[Ah] 대비 얼마나 벗어났는지(%). 기준표가 `ChargeProgramSpec`에 없으면(아직 업로드 안 됨/해당 바이어 코드 없음) NULL — 이 경우 그 로트는 1단 회귀에서 제외된다. `POST /api/charge-program/upload`로 기준표를 올려야 하며, 한 번도 안 올리면 공정 데이터가 아무리 많아도 1단·2단 회귀가 표본 부족으로 실행되지 않는다).
  - **`fill_weight`·`water_loss`(및 이로부터 만든 `fill_per_rated`, `water_loss_rate`)는 1단 X에서 제외한다.** 이유(더미 데이터로 실제 확인됨): Y(잔존율)를 `(fill_weight − water_loss) / fill_weight`로 계산하는 이상, 이 두 컬럼을 다시 X로 넣으면 Y와 완전공선(상관계수 −1.0에 가까움, 항등식)이 되어 회귀 자체가 무의미해진다. **Y를 구성하는 변수를 그 Y의 예측변수로 다시 쓰지 않는다**는 원칙을 반드시 지킨다.
  - `bath_no`·`circuit_no`는 회귀계수를 볼 인자가 아니라 **통제/층(group) 변수**다 — 동일 조·회로 로트는 서로 독립이 아니므로(§8 참조), 조·회로별 잔차 분포를 별도로 표시한다.
- **정규화(기존 Open Question 4 해결, §6-③-정규화 참조)**: `charge_amount`는 정격용량과 상관 0.995로 사실상 "모델 크기"이므로 원본 대신 `charge_ratio`(무차원 비율)를 사용한다. 실측 확인 결과 `charge_ratio`와 `rated_capacity`의 상관은 0.043으로 낮아져 모델 크기 효과가 제거됨을 확인했다.
- 회귀 실행 시 **VIF(분산팽창계수) 산출·표시**를 대시보드에 추가한다 — 다중공선성이 남아있는지 시각적으로 확인하기 위함.
- KPI 카드(예: 평균 잔존율(Y), 이번 달 Y/Z 부적합 건수, 매칭률 등)를 상단에 노출한다.

**③-2 분석 대시보드 — X+Y → Z (20시간 용량) 회귀 + 베이스라인**
- **Z = `discharge_amount`(20시간율 실측 방전용량, Ah)로 확정**한다. 근거(§10-1 참조): `capacity_rate ≒ discharge_amount / rated_capacity × 100` (두 값의 차이가 반올림 오차 수준). 따라서 `discharge_amount`가 Z의 절대값, `capacity_rate`는 그 %-표현이다.
- **2단 입력**: 1단과 동일한 X셋 + Y(잔존율, 실측 기반). **학습은 반드시 "실측 Y"로 한다.** 예측된 Ŷ로 학습하면 1단 오차가 2단에 그대로 각인되어 편향이 누적되기 때문이다(train-inference mismatch, §8 리스크로 기재).
- **추론(운영) 시에만** 1단의 예측값 Ŷ를 2단에 투입해 Z를 구한다. 이때 산출된 Z 예측값에는 반드시 "Ŷ 기반" 플래그를 붙여, 실측 Y로 구한 예측과 구분한다.
- **베이스라인 모델을 함께 만든다: X → Z 직접 회귀.** 캐스케이드(X→Y→Z)가 이 베이스라인보다 실제로 더 나은지 비교해야 "포화도가 성능의 매개변수다"라는 이 과제의 전제가 검증된다. **더미 데이터로 확인한 주의사항**: 이번 더미셋에서는 잔존율(Y)과 capacity_rate(Z%)의 상관이 0.23으로 약하다 — 즉 이 특정 더미 데이터만 놓고 보면 "포화도가 성능을 강하게 매개한다"는 가설이 뚜렷하게 뒷받침되지는 않는다. 그렇기 때문에 베이스라인 비교 구조가 더더욱 필요하다(수치 비교 자체는 v2로 이관하되, 모델 구조와 저장 스키마는 MVP에서부터 자리를 만든다).
- 시험 매칭 로트(59개)만이 2단(및 베이스라인) 학습 데이터다. 미매칭 41개는 학습에 기여하지 않는 **순수 추론 대상**임을 화면에도 명확히 구분해 표기한다.
- **1단과 2단의 갱신 주기가 다르다는 것을 반드시 설계에 반영한다(담당자 확인 사항, 중요).** X(공정인자)는 생산할 때마다 나오므로 사실상 매달(또는 그보다 자주) 갱신되고, Y(잔존율 proxy)는 X만으로 계산되는 값이라 X와 동일한 주기로 항상 함께 확보된다. 반면 **Z(시험 실측값)는 매 로트·매달 나오는 것이 아니라 월 1회 또는 분기(3개월)에 한 번꼴로만 갱신**된다. 따라서:
  - **1단(X→Y) 모델은 매달 재학습이 가능**하다 — 그 달 생산된 로트 전체(공정 데이터)로 즉시 Y를 계산·재학습할 수 있다.
  - **2단(X+Y→Z) 모델과 베이스라인(X→Z)은 새 시험 데이터가 들어오는 주기(월/분기)에만 재학습 가능**하다. 즉 이번 달 예측 화면에 쓰이는 2단 계수가 "이번 달 것"이 아니라 "가장 최근 시험 주기의 것"일 수 있다.
  - 화면·이력(AnalysisRun)에는 **stage별로 별도의 "최근 학습 시점"을 표시**해야 한다(예: "1단 모델: 2026-09 갱신" / "2단 모델: 2026-Q3(최근 시험 기준) 갱신"). 하나의 "분석 실행일"로 뭉뚱그려 표시하면 담당자가 2단 계수의 신선도를 오인할 수 있다.

**③ 공통 — 감액 분해 로직 (신규, MVP 범위)**
- `water_loss`를 통값으로만 보지 않고, 이론적 기대치와 비교해 분해한다. `charge_amount`(→`overcharge_ah = charge_amount − rated_capacity`)만 있으면 구현 가능하므로 MVP 범위에 포함한다.
  ```
  theoretical_water_loss = 0.336 * overcharge_ah   # 과충전 1Ah당 물 전기분해 손실(g), 도메인 상수
  water_loss_residual    = water_loss - theoretical_water_loss
  ```
- **더미 데이터 검증 결과(중요, 반드시 담당자 확인 필요)**: 이 더미셋에서 `overcharge_ah`는 평균 11.7Ah(4.2~19.6Ah)로 계산되고, 이에 따른 `theoretical_water_loss`는 평균 3.9g에 불과하다. 반면 실제 `water_loss`는 평균 521g으로, **이론치 대비 약 139배** 크다. 즉 이번 더미 데이터에는 도메인 상수(0.336g/Ah)를 그대로 적용할 수 없는 단위·정의 불일치가 있다(§10-1 참고). 로직 자체(잔차 계산 구조)는 MVP에 구현하되, **잔차값의 절대 크기 해석은 실제 SOP 확인 전까지 보류**하고 화면에도 "참고용, 검증 전" 표기를 한다.
- 잔차 해석 규칙(구조만 구현, 임계값은 실 데이터로 추후 튜닝):

  | 잔차(residual) | 해석 |
  |---|---|
  | 크게 (+) | 증발·산 미스트·누액 과다 의심 |
  | 0 근방 | 정상 |
  | 크게 (−) | 화성 부족·계량 오류·(AGM 특성상) 산소 재결합 과다 가능 |

  > AGM은 VRLA(밀폐형)라 산소 재결합 반응으로 실측 water_loss가 이론치보다 작게 나올 수 있다는 점을 원인진단 문구에 단서로 남긴다.

**③-3 상세 분석 — 형명(모델)별 X·Y·Z 한눈에 보기 (신규)**
- ③-1·③-2에서 나온 전체(집계) 회귀결과를 **형명(model_name) 단위로 쪼개서 비교**하는 화면. 정격용량 6개 용량군(50/60/70/80/90/105Ah), 총 35개 형명 각각에 대해 주요 X 인자 평균, Y(잔존율), Z(capacity_rate)를 한 표에서 비교한다.
- 용량군 요약 카드(형명 수, 평균 Y, 평균 Z, Y/Z 부적합 형명 수) + 형명별 상세 테이블(로트 수, X 인자 평균, Y/Z 값과 SPEC 판정 배지)로 구성한다.
- **형명 간 비교는 반드시 무차원화된 인자(충전율 등)로 해야 한다** — `charge_amount`·`fill_weight` 원본을 그대로 비교하면 모델 크기 차이(다중공선성)를 공정 차이로 오인하게 된다(§6-③ 정규화 원칙과 동일).
- 시험 데이터가 없는 형명(그 달 매칭 로트가 0건인 모델)은 Z를 "미시험"으로 표시하고 부적합과 구분한다.
- 이 화면은 ③-1·③-2의 회귀결과를 다른 각도(형명별 분해)로 보여주는 것이므로 별도의 학습 로직은 없다 — AnalysisRun 결과를 `model_name`으로 group-by한 조회 화면이다.

**③-4 상세 분석 — 형명별 Y(포화도) 추이 그래프 (신규)**
- **데이터 누적 저장 원칙**: 매달 업로드되는 `ProcessData`·`TestData`·이로부터 계산된 `LotDerived`(잔존율 Y 포함) 레코드는 **덮어쓰지 않고 계속 쌓는다(append-only)**. 이렇게 누적된 로트별 이력이 있어야 시간 흐름에 따른 Y 추이를 그릴 수 있다 — 이번 개정에서 확정하는 핵심 저장 원칙이다.
- `process_data.csv`에 이미 `prod_date`(생산일자) 컬럼이 존재하므로(실측 확인: 더미 데이터는 2026-01-01 ~ 2026-12-28 범위), 추가 컬럼 없이도 **일간·월간·연간 단위 집계**가 가능하다.
- 형명(모델) 선택 시 해당 형명 로트만 필터링한 Y 추이를, "전체 평균" 선택 시 전체 로트 평균 Y 추이를 그래프로 보여준다. 단위는 **일간/월간/연간 토글**로 전환한다.
- 그래프에는 SPEC 하한선을 기준선으로 함께 표시해, 추이가 SPEC에 가까워지거나 이탈하는 흐름을 시각적으로 바로 확인할 수 있게 한다.
- **연간 추이는 최소 2개 연도 이상 데이터가 누적되어야 의미가 생긴다** — 첫 해에는 "연간" 탭에 아직 비교할 과거 연도가 없다는 안내를 표시한다(§8 엣지케이스 추가).
- 이 그래프는 별도 학습이 필요 없는 **단순 시계열 집계 조회**다(1단/2단 회귀모델 학습과 무관). `LotDerived.retention_rate`를 `prod_date` 기준으로 group-by해서 그린다.

**④-1 예측 — 미매칭 로트 Y(포화도) 일괄 산출**
- ①에서 시험과 매칭되지 않은 41개 로트에 대해, 1단 회귀모델(X→Y)을 이용해 잔존율(Y)을 일괄 산출한다.
- 담당자가 인자값을 수동으로 입력해 특정 조건에서의 Y도 즉시 계산할 수 있다.

**④-2 예측 — Ŷ 기반 Z(20시간 용량) 일괄 예측**
- ④-1에서 산출한 Ŷ와 X를 2단 회귀모델에 넣어 Z(`discharge_amount`, `capacity_rate`)를 예측한다. 결과 목록에는 "Ŷ 기반" 플래그를 표시한다.
- 더미 데이터 기준 매칭률은 59%(100개 중 59개 매칭)이므로, 나머지 41개 로트가 ④-1·④-2의 일괄 예측 대상이다.

**⑤ SPEC 판정 & 원인진단 (Y·Z 양쪽 확장)**
- 예측/실측 **Y(잔존율)**와 **Z(discharge_amount / capacity_rate)**를 각각 SPEC 기준과 비교해 양품/부적합을 판정한다. SPEC 하한은 **정격용량(모델)별로 다를 수 있어** 모델 단위로 설정 가능해야 한다. (기존 PRD는 포화도만 판정하도록 되어 있었음 — 이번 개정에서 Z도 판정 대상에 추가)
- 부적합(또는 저Y·저Z) 판정된 로트에 대해, "회귀계수 × SPEC 이탈 정도"를 기준으로 영향력이 큰 인자 순으로 원인 인자를 자동 지목한다. Y 부적합과 Z 부적합은 원인 인자셋이 다를 수 있으므로 구분해서 지목한다.
- 지목된 원인 인자에 대해 규칙 기반 개선 권고 문구를 함께 제시한다. **원인진단 규칙이 무조건 "주액량 증대"로 귀결되지 않도록 설계**한다 — 액 부피는 거의 변하지 않아도 화성으로 극판 공극(분모)이 커지면서 포화도가 떨어지는 경우가 실제로 많기 때문이다.
- **(신규, 2026-09-21, history/20) EN/SAE CCA 규격 합격여부 판정은 Y·Z SPEC 판정과 별개의 로직이다.** `ConstantsByModel.spec_lower_y/z`처럼 모델별로 설정하는 값이 아니라, EN 50342/SAE J537이 정한 **형명 무관 고정 전압·시간 임계값**(§7 `TestData.en_cca_10s_voltage`/`en_cca_6v_hold_sec`/`sae_cca_7v2_hold_sec` 참조)과 비교해 합격/불합격만 배지로 노출한다. 표본이 극히 적어(§7 참조) 원인진단(회귀계수×이탈도 기반 인자 지목)의 대상은 아니다 — 대시보드·상세분석 화면에 "참고 정보"로만 표시.

## 9. 성공 지표

- **시간 단축**: 월 분석 소요시간 10시간 → 2시간 이내 (80% 이상 단축)
- **파이프라인 완결성**: 집체 3일 종료 시점, ①~⑤ 전체(1단·2단·베이스라인 포함)가 실제 데이터로 오류 없이 1회 이상 종단간 실행됨
- **예측 커버리지 재정의**: X 인자셋을 `process_data.csv` 컬럼으로 한정한 뒤, **시험 미매칭 41개 로트의 Y·Z 산출률 100%**
- **캐스케이드 구조 완결성**: X→Y→Z 캐스케이드와 X→Z 베이스라인이 **둘 다 구현**되어 있을 것 (정량적 우열 비교는 v2에서 수행)
- **이상 로트 탐지 확인**: `water_loss_residual` 분포로 이상 로트가 실제로 1건 이상 검출되는지 확인 (절대값 해석은 §6-③ 단서에 따라 보류하되, 상대 순위로 이상 탐지 로직 자체는 검증)
- **재현성**: 동일 입력값에 대해 원인진단 결과가 담당자와 무관하게 항상 동일(규칙 기반이므로 100% 재현 가능해야 함)
- **이력 축적**: 분석 실행마다 AnalysisRun 이력이 `stage`(1단/2단/베이스라인) 구분과 함께 SQLite에 누락 없이 기록됨

> 참고: 예측 모델의 R²/RMSE 등 정확도 지표, 그리고 캐스케이드 vs 베이스라인의 정량적 성능 비교는 이번 MVP 성공 기준에서 **의도적으로 제외**했습니다(v2로 이관). 3일 내 "정확한 예측"이 아니라 "종단간 동작하는 2단 파이프라인 + 이력화 + 비교 구조 마련"이 목표이기 때문입니다.

## 10. 미해결 질문 (Open Questions)

### 이번 더미 데이터 분석으로 확인된 패턴 (방법론은 채택, 구체적 수치는 실 데이터로 재검증 필요)

1. **Z(20시간 용량) 후보 판별** → **해결**: `capacity_rate`(diff 평균 −0.006, 표준편차 0.041, 반올림 오차 수준) = `discharge_amount / rated_capacity × 100`이 거의 완벽히 성립. `charge_rate`(diff 평균 −0.006, std 0.044)도 `charge_amount_20h / discharge_amount × 100`으로 거의 완벽히 성립. 반면 `capacity_rate`와 `charge_amount_20h`의 관계는 diff std 3.53으로 훨씬 느슨함. **결론: Z = `discharge_amount`(실측 20시간율 방전용량, Ah), `capacity_rate`는 그 %-표현. `charge_amount_20h`는 Z가 아니라 충전효율(`charge_rate`) 산출용 예비충전량.**
2. **모델별 정규화 필요성 및 방법** → **해결**: `charge_amount`(r=0.995)·`fill_weight`(r=0.992)·`cell1_weight`(r=0.993)·`mt_current`(r=0.965)·`water_loss`(r=0.889, 신규 확인)가 모두 정격용량과 강상관. `fill_per_rated`·`charge_ratio`·`water_loss_rate`로 정규화한 뒤 재확인한 결과 정격용량과의 상관이 0.004~0.043 수준으로 낮아짐 — **통계적 표준화가 아니라 물리적 무차원화(비율화)로 다중공선성을 해소**하기로 확정.
3. **모델 개수 오류 정정** → 기존 PRD가 "28개 모델"이라 기재했던 것은 오류. `process_data.csv` 실측 기준 **35개 모델**(50/60/70/80/90Ah 각 6개, 105Ah 5개, 총 6개 용량군)이 정확한 수치.
4. **1단 X셋에서 Y 구성요소 제외 필요성(신규 발견)** → **해결**: `water_loss`/`fill_weight`는 Y(잔존율)를 정의하는 변수이므로 1단 X에서 제외해야 함(포함 시 상관 −1.0의 항등식). 회귀 대상 X는 `electrolyte_temp`·`tank_temp`·`soaking_time_sec`·`aging_days`·`formation_dv`·`cell_weight_mean/std`·`charge_ratio`로 확정.
5. **`MT(V)`·`MT(A)`의 정체** → **해결(담당자 확인)**: 공정 설정값이 아니라 **시험 단계에서 별도로 측정하는 값**. 목적은 (1) 화성 후 전압(`voltage_2nd`, "완성전압")과 차이가 있는지 확인하고 (2) 간이 CCA(저온시동전류) 측정을 통해 완성 용량이 높을지 낮을지 방향성을 사전에 가늠하는 것. 데이터로도 뒷받침됨: `mt_current`와 `initial_cca`의 상관은 **0.957**로 사실상 같은 계열의 지표이며, `mt_voltage`는 `voltage_2nd`보다 평균 **0.25V 낮게** 나타남(로트 평균, 보관 중 자연방전 영향으로 추정). 다만 `mt_current`는 배터리 크기(정격용량)와도 강상관(r=0.965)이라 원값 그대로는 `capacity_rate`와의 직접 상관이 약함(r=0.036) — "용량 방향성"을 실제로 스크리닝하려면 모델(정격용량)별로 정규화한 값으로 봐야 함. 시험 시에만 얻어지는 값이므로 **1단(X→Y) 예측 인자에서는 계속 제외**하고(미매칭 로트에는 값 자체가 없음), 매칭된 59개 로트에 한해 "시험 로트 한정 심층 분석"용 조기 스크리닝 지표(완성전압 대비 전압차, 모델 정규화 CCA)로 다룬다.

### 여전히 담당자 확인이 필요함 (데이터만으로는 해결 불가)

6. **사내에서 "포화도"라고 부르는 값의 실제 정의** → **부분 해결(담당자 확인)**: 기준(basis)은 셀 전체/세퍼레이터 중 하나로 고정된 게 아니라 **사양(모델/스펙)마다 다르게 관리**되며, 소스(source)는 **관리 타겟은 계산형(이론치)이지만 실측도 병행**한다는 것까지 확인됨 — `saturation_basis`·`saturation_source`를 열거형으로 둔 기존 스키마 설계가 유효함이 확인된 셈이다. **다만 정확한 계산식(공극 부피를 어떻게 산출하는지)은 담당자도 정확히 모르고 설계 기밀일 가능성이 있다고 답변받음.** 남은 미해결 부분: (a) 모델별로 어떤 basis를 쓰는지 매핑표, (b) 계산식·공극 상수 자체의 확보 가능 여부(사내에서도 비공개일 수 있어 **v2에서 확보된다고 가정하지 않는다** — 확보 실패를 기본 시나리오로 두고 잔존율 proxy를 장기적으로도 유지할 수 있는 설계를 우선한다).
7. **`water_loss` 측정 SOP** — 측정 시점(주액 직후/흡수 후), 저울 분해능, 동일 저울 사용 여부. 이론적 전기분해 손실량(평균 3.9g)과 실측 `water_loss`(평균 521g)가 약 139배 차이나는 현상을 설명하려면 이 SOP 확인이 필수. (139배의 의미: 이론식 `0.336g × 평균 과충전량 11.7Ah ≈ 3.9g`인데 실측 감액량은 평균 521g으로, 이론식이 예측하는 것보다 실측값이 약 139배 더 크다는 뜻 — 즉 이 도메인 상수를 이번 더미 데이터에 그대로 적용하면 안 된다는 신호. water_loss가 화성 중 전기분해뿐 아니라 6~9일 에이징 기간의 증발·흡습 등 다른 감액 경로까지 포함해 측정됐을 가능성이 유력함.)
8. **과충전 Ah 산출 방식** — `charge_amount`가 정격용량 대비 순수 초과분(과충전량)인지, 총 화성 충전 Ah인지, 아니면 전혀 다른 정의인지. **데이터로 추가 확인**: `charge_amount / rated_capacity`(charge_ratio) 비율이 전 로트에 걸쳐 **107~123%(평균 115%, 표준편차 3.1%p)**로 매우 좁은 범위에 몰려 있음 — 이는 `charge_amount`가 로트마다 자유롭게 변하는 실측치라기보다, **"정격용량의 약 110~120%까지 충전한다"는 화성 충전 레시피(목표값)에 가깝다**는 강한 정황 증거. 이 경우 `charge_amount − rated_capacity`(≈ 정격의 약 15%)를 과충전량으로 근사한 것은 데이터상 합리적이나, 정확한 공정 정의(레시피 기준 충전량인지/실측 충전량인지)는 SOP로 최종 확인이 필요함.
9. **화성 후 비중 데이터 확보 가능 여부** — 확보되면 `docs/domain-constants.md`의 "액 질량 역산식"으로 실제 액 부피 추정이 가능해짐.
10. **모델별 공극부피 상수(세퍼레이터 사양·극판 공극률) 확보 가능 여부** — 확보되면 `saturation_calc`(실제 포화도)를 v2에서 활성화할 수 있음.
11. **Y와 Z 각각의 SPEC 하한값** (모델/정격용량별로 다른지 포함) — 더미 데이터의 분포(예: capacity_rate 평균 97.7%)는 통계일 뿐 실제 SPEC 기준치가 아님.
12. **원인 인자 동률/복수 지목 시 처리 규칙** — "회귀계수×SPEC이탈" 값이 여러 인자에서 비슷하게 높을 때, 몇 개까지 지목할지, 어떻게 우선순위를 매길지 구체적 규칙이 필요.
13. **유관부서 열람 경로** — 담당자 PC를 사내망 IP로 공유해 접속하는 방식인지, 결과를 파일/보고서로 내보내 공유하는 방식인지 확정 필요(전자라면 SQLite 동시 읽기/쓰기 충돌 방지 설계가 3일 범위에 추가되어야 함).
14. **시험 데이터의 실측 시각(`tested_at`)** — 더미 `test_data.csv`에는 시험 일시 컬럼이 없음. 실제 데이터에는 존재하는지, 이력·추세 조회에 필요한지 확인 필요.
15. **시험(Z 데이터) 주기의 정확한 확정** — 담당자 확인: X(공정)·Y(잔존율)는 매달 갱신되지만 Z(시험 실측)는 "월 1회 또는 분기(3개월) 1회" 정도로 X보다 드물게 갱신된다고 확인됨. 정확히 월 단위인지 분기 단위인지, 아니면 비정기적인지에 따라 2단(X+Y→Z) 모델의 재학습 트리거 조건(캘린더 기반 vs 새 시험 데이터 업로드 기반)이 달라지므로 확정이 필요함. MVP는 "새 시험 데이터가 업로드될 때마다 2단을 재학습"하는 이벤트 기반으로 설계해 캘린더 주기와 무관하게 동작하도록 함.
16. **형명별 상세 분석(③-3)의 최소 표본 임계값(n)** — `docs/correlation-reliability-review.md` §4에서 확인됨: 더미 데이터 기준 형명당 표본이 중앙값 2건(공정)·1건(시험)으로 매우 작아, 표본이 부족한 형명에 SPEC PASS/FAIL 배지를 그대로 노출하면 오해를 부를 수 있음. "표본 부족 — 참고용"으로 전환할 최소 n 기준(예시로 5건 제시)을 담당자가 실제 운영 감각에 맞춰 확정해야 함. 실제 데이터에서도 형명별 생산량 편차가 크면 동일한 문제가 재발할 수 있으므로 임계값은 설정 가능한 값으로 둘 것.
17. **회귀결과에 통계적 유의성(p-value/신뢰구간) 표시 여부** — `docs/correlation-reliability-review.md` §1에서 확인됨: 더미 데이터에서는 전해액온도·수조온도가 Y(잔존율)에 통계적으로 유의하지 않은데도(p>0.3), 상관계수 크기만 보면 영향인자처럼 보일 수 있음. 대시보드·원인진단 화면에 유의성 검정 결과(p-value 배지 등)를 함께 표시해 "노이즈성 상관"을 걸러낼지, 아니면 회귀계수 크기 기준만 유지할지 결정 필요.
18. **포화도(공극 기준) 정의의 SOC·압착률 전제 조건 미확정** — §1-1 용어 정의는 "총 공극 = 세퍼레이터 공극(압착 상태 기준) + 극판 공극(화성 후 기준) + 자유 공간"까지는 명시했으나, (a) 이 정의가 어느 SOC(충전 상태) 기준인지(예: 만충 기준인지), (b) 세퍼레이터 "압착 상태"의 정량적 압착률이 얼마인지는 아직 담당자 확인이 없다. `saturation_calc`가 v2에서 실제로 활성화될 경우(§10-6, `docs/domain-constants.md` 참조) 이 두 전제 조건이 확정되지 않으면 계산 자체가 불가능하므로, 계산식·공극 상수 확보 여부(§10-6, #9, #10)와 함께 반드시 같이 확인해야 하는 항목으로 남긴다.
19. **`model_name` 접미 문자(S/H/K 등)가 실제로 "바이어(고객사)"를 의미하는지** (신규, §6-② 그룹 일괄 입력 관련) — 더미 데이터 분석 결과, `model_name`의 밑줄 뒤 문자(예: `AGM105_S1`의 `S`)는 `lot_id` 마지막 2자리(문자+숫자, 예: `...S3`)의 앞 문자와 100% 일치했다(31/28/41건 전수 일치, 문자 자체만 — 뒤 숫자는 다름). 즉 이 문자는 `lot_id`에도 동일하게 인코딩된 안정적인 구분 코드이며, 현재 담당자 요청("형명+바이어가 같으면 같은 그룹")을 만족시키는 유일한 후보로 보고 **이번 MVP는 이 문자를 "바이어/스펙 구분 코드"로 간주하고 `model_name` 전체를 그룹 키로 사용**한다(즉 형명이 이미 바이어 구분을 포함하므로 별도 컬럼을 추가하지 않는다). 다만 이 문자가 실제로 고객사(바이어)를 뜻하는지, 아니면 다른 스펙 축(예: 극판 사양)을 뜻하는지는 데이터만으로 확정할 수 없어 **담당자 확인이 필요**하다. 확인 결과 "바이어"가 아니거나 별도 컬럼이 필요하다고 판명되면 `Lot`에 `buyer_code` 컬럼을 추가하는 마이그레이션이 필요할 수 있다.
20. **그룹값과 다른 값이 필요한 예외 로트의 처리 방법** (신규, 2026-09-10, §6-② 관련) — 로트별 개별 입력 UI를 제거하고 그룹 일괄 입력만 남기기로 했다(2026-09-10, `output/01_upload_matching.html`에 통합). "수기입력을 별도 화면으로 분리할지"는 **해결됨** — 별도 화면 없이 업로드·매칭 화면에 통합하기로 확정했다. 다만 **그룹값과 다른 값이 필요한 예외 로트를 고칠 화면상 경로가 없다는 문제 자체는 여전히 미해결**이다. 이번 더미셋의 미입력 2건은 그룹 일괄 입력으로 모두 해소되지만, 실제 운영에서 같은 그룹(형명, 또는 형명+생산일자) 안에서 유독 값이 다른 로트가 생기면 대응 UI가 없다. CSV를 정정해 재업로드하는 방법으로 대응할지, 예외 편집 기능을 다시 넣을지 결정이 필요하다(백엔드의 `GET/PUT /api/lots/{lot_id}/manual-fields` 개별 편집 API 자체는 존치하되 화면에 연결하지 않은 상태 — `.docs/02_nextjs-fastapi-구현-아키텍처.md` 참조).
