# 세션 진행 요약 (2026-09-10)

> 이 문서는 이번 작업 세션에서 무엇을, 왜 바꿨는지를 한 곳에 정리한 로그입니다. 각 항목의 최신 상세 내용은 해당 원본 문서를 기준으로 삼으세요 — 이 문서는 "무슨 일이 있었는지"를 빠르게 훑기 위한 색인입니다.

## 1. 무엇을 했나 (시간순)

1. **최초 요청**: 최종 결과물 중 가장 중요한 화면을 HTML로 만들어 `output/`에 저장 → 분석 대시보드 목업 제작.
2. **포화도 개념 재정의 요청**: "포화도 = 감액량으로 인한 잔여 액량" 개념으로 다시 잡아달라는 요청 → 질문 던짐(계산식, 시점, capacity_rate와의 관계, 방향성).
3. **2단 캐스케이드 구조로 대개편**: 사용자가 제공한 상세 프롬프트(`클로드코드_프롬프트_PRD기획서_수정.md`)를 반영해 `prd.md`와 기획서 docx를 X→Y→Z 2단 캐스케이드 구조로 전면 재작성. `process_data.csv`/`test_data.csv`를 직접 재분석해 실측값으로 재작성함(추측 금지).
4. **후속 질문 답변 반영**: MT(V)/MT(A)의 정체(시험 전용 측정값, 완성전압 비교·간이 CCA 용도), water_loss 139배 불일치 설명, charge_amount 출처 추정(정격의 107~123% 충전 레시피로 추정) 등을 데이터로 검증해 반영.
5. **더미 데이터 유의사항 강화**: "모든 수치는 더미 데이터 예시일 뿐"이라는 경고를 문서 상단과 HTML 화면 배너에 명시.
6. **HTML 목업 전체 재작성**: `output/analysis_dashboard.html`, `01_upload_matching.html`, `02_manual_entry.html`, `04_prediction.html`을 2단 캐스케이드에 맞춰 재작성. 이후 사용자 피드백으로 "수동 입력 예측" 탭이 필수 입력이 아니라 선택적 시뮬레이션임을 명확히 하는 안내 추가.
7. **1단/2단 갱신 주기 차이 반영**: X·Y는 매달, Z(시험)는 월1회~분기1회로 갱신 주기가 다르다는 제약을 PRD·데이터모델(`AnalysisRun.is_latest_for_stage`)·HTML(모델별 갱신 시점 분리 표시)에 반영.
8. **상세 분석 화면 신규 추가**: 형명(모델)별 X·Y·Z를 한눈에 보는 `output/03_detail_analysis.html` 제작(용량군 요약 카드 + 35개 형명 테이블). 실제 더미 CSV를 형명별로 집계한 값 사용.
9. **누적 저장 + 추이 그래프 추가**: append-only 저장 원칙을 PRD에 명시하고, `03_detail_analysis.html`에 형명별 Y 추이(일간/월간/연간, inline SVG) 섹션 추가. `prod_date`(2026-01-01~12-28, 1년치)를 이용해 실제 월별 평균으로 그래프 작성.
10. **ML/Colab 사용 여부 검토**: Colab은 사외반출 금지 원칙상 실사용 불가, 표본 규모(월 4만 건 X vs 연 수백~1,000건 Z)를 감안하면 복잡한 ML보다 해석 가능한 회귀 유지가 맞다는 결론 → `prd.md`에 반영.
11. **상관관계 결과 통계적 신뢰성 검증**: 피어슨 r + p-value를 직접 계산. 전해액온도·수조온도의 Y 영향은 유의하지 않음(p>0.3), Y→Z 매개 가설도 p=0.083으로 미확정, 형명별 상세분석 표본이 매우 작다(중앙값 1~2건)는 것을 확인 → 별도 문서로 정리.
12. **Streamlit → Next.js 기술 스택 로드맵 확정**: 3일 MVP는 Streamlit, 이후 디자인 완성도를 위해 Next.js+FastAPI로 전환하기로 결정. 마이그레이션 대비 코딩 규칙(분석 로직/UI 코드 분리)을 명시.
13. **문서 분리**: `prd.md`를 CLAUDE.md가 정의한 표준 구조(§1~§10)만 남기고, 부속 내용은 `domain-constants.md`(도메인 상수), `correlation-reliability-review.md`(통계 검증 리포트)로 분리. 실행 로드맵·ML 전략·기술스택 로드맵은 기획서 docx 부록으로 이전.
14. **CLAUDE.md 갱신(`/init`)**: 저장소 최신 상태(문서 분리 구조, 기술 스택 결정, 2단 캐스케이드 도메인 사실)를 반영해 전면 재작성.
15. **포화도 정의 최종 답변 반영**: 담당자 확인 — 기준(셀/세퍼레이터)은 사양마다 다르게 관리, 타겟은 계산형(이론치)+실측 병행, 단 정확한 계산식은 설계 기밀일 가능성 있음 → `saturation_basis`/`saturation_source` 스키마 설계가 실제와 일치함을 확인. `saturation_calc` 활성화를 "확정 v2"가 아니라 "확보 실패 가능성 있는 스트레치 목표"로 하향 조정.

## 3. 핵심 설계 결론 (요약)

- **파이프라인**: X(공정인자) → Y(포화도, 잔존율 proxy) → Z(20시간 용량, discharge_amount/capacity_rate) 2단 캐스케이드 + X→Z 베이스라인 병행.
- **Y 정의**: 잔존율 `(fill_weight − water_loss) / fill_weight × 100`을 근사치로 사용. 실제 포화도(공극 기준)는 계산식이 기밀일 수 있어 장기적으로도 이 proxy가 주력일 수 있음.
- **1단 X셋**: `process_data.csv` 컬럼만 사용(전해액온도·수조온도·함침시간·에이징일수·화성전압차·셀중량평균/표준편차·충전율). `fill_weight`/`water_loss`(Y 구성요소라 제외), `MT(V)`/`MT(A)`(시험 전용이라 제외).
- **학습 규칙**: 2단은 항상 실측 Y로 학습, 추론 시에만 예측 Ŷ 투입(Ŷ 기반 플래그 필수). 1단/2단은 갱신 주기가 다름(매달 vs 월1회~분기1회).
- **통계적으로 신뢰 가능한 것**: 충전율·셀중량표준편차→Y, 전해액온도·충전율·수조온도→Z, 무차원화가 다중공선성 해소. **불확실한 것**: 전해액온도·수조온도→Y(유의하지 않음), Y→Z 매개 가설(p=0.083), 형명별 상세분석 표본(중앙값 1~2건).
- **기술 스택**: 3일 MVP는 Streamlit(분석 로직은 UI와 분리된 Python 모듈로), 이후 Next.js+FastAPI로 전환(디자인 완성도 목적).
- **데이터 원칙**: 사외반출 금지(Colab 등 클라우드 사용 불가), append-only 누적 저장, 더미 데이터 수치를 실제 값처럼 하드코딩하지 않기.
