# 36. 충전 프로그램 바이어 제한 공정/시험 더미 데이터 생성 계획

## 배경/동기

이 컴퓨터는 저장소를 새로 클론한 환경이라 `process_data.csv`/`test_data.csv`, 실제 충전
프로그램 원본("★ 260428 AGM CF 충전 프로그램 3.xlsx")이 전혀 없고 데모 DB(`backend/db/app.db`)도
비어 있는 상태(`Lot`/`ProcessData`/`TestData`/`ChargeProgramSpec` 전부 0행, 확인 완료)다.
사용자가 파이프라인 확인·시연용으로 신규 더미 데이터를 요청했다.

## 범위

- 공정 데이터 약 5,000행 — `model_name`의 바이어 코드를 충전 프로그램에 실제로 등재된 조합으로만
  제한(2026-09-26 세션에서 실제 충전 프로그램 엑셀을 파싱해 확인한 뒤 CLAUDE.md에 기록해 둔
  (정격용량, 바이어) 37개 조합을 그대로 재사용 — 원본 엑셀 파일 자체는 이 컴퓨터에 없어 재파싱 불가,
  Desktop/Downloads/Documents도 확인했으나 없음).
- 시험 데이터 300건 — 전량 20시간율(Z, discharge_amount 등) 포함, 150건은 EN CCA 체크포인트만,
  나머지 150건은 SAE CCA 체크포인트만 채움(둘 다 채우지 않음 — 실측도 샘플마다 어떤 신뢰성
  서브시험을 탔는지 갈리는 것과 동일한 설계).
- 업로드는 이번 범위에서 실행하지 않음(스크립트+파일 생성까지, 실제 반영은 사용자 확인 후).

## 방법

- 기존 `scripts/generate_agm60_70_dummy.py`/`generate_charge_buyer_dummy.py`와 동일한 통계 로직
  재사용: 공정 조건(전해액온도·수조온도 등)은 전체 풀 공통분포, 용량비례 컬럼(fill_weight 등)은
  용량군별 분포, Y/Z/CCA는 `docs/correlation-reliability-review.md` 실측 검증 방향·크기 그대로
  수식+노이즈로 생성. 단, 원본 `process_data.csv`가 없어 공정조건 풀 분포(평균/표준편차)는
  실측 재계산이 아니라 도메인상 타당한 추정값을 사용(회귀가 학습할 상대적 신호 구조는
  동일하게 보존됨 — 절대 스케일의 실측 정합성만 낮아짐, 아래 "알아두면 좋은 점" 참고).
- **산출 포맷**: 시험 데이터는 요청대로 `.xlsx`(raw 신뢰성 시험 워크북 구조,
  `backend/etl/test_raw.py` 파서와 1:1 대응 — 그대로 업로드하면 완전히 동작). 공정 데이터는
  `.xlsx`가 아니라 `.csv`로 저장 — `backend/etl/process_raw.py`가 raw 엑셀 경로에서
  `electrolyte_temp`/`charge_amount`/`tank_temp` 3개 필드를 원천적으로 코드 레벨에서 항상
  `None`으로 고정하기 때문에(실제 현장 raw 파일에도 이 3개 필드가 없어서 그런 것 — 파일을
  아무리 잘 만들어도 우회 불가), 공정 데이터를 raw 엑셀로 만들면 업로드는 성공하지만 1단
  회귀에 필수인 `charge_ratio`(charge_amount 기반)와 전해액/수조온도가 전부 비어 회귀가 아예
  안 돈다. 기존 두 더미 스크립트가 전부 공정 데이터만 CSV로 저장해 온 것도 이 이유 — 동일한
  이유로 이번에도 CSV를 유지한다(CSV도 업로드 API가 바로 받는 포맷이라 "업로드 즉시 가능"
  목표 자체는 그대로 달성됨).
- 생성 스크립트는 `scripts/` 관례를 따라 신규 파일로 작성하고, 산출물은 저장소 루트에 저장
  (`.gitignore`가 이미 `*.csv`/`*.xlsx`를 제외하므로 git에는 안 잡힘).

## 완료 기준

- 공정 CSV 약 5,000행(37개 조합 × 135행), `model_name`의 바이어 코드가 문서화된 37개 조합에만
  국한됨을 스크립트 assert로 검증.
- 시험 xlsx 300건, discharge_amount(20시간율) 전량 채움 + EN CCA 150건/SAE CCA 150건 정확히
  분리(체크로 검증), 조합별로 8~9건씩 분산.
- 두 파일 모두 실제 업로드 API(`POST /api/upload/process`, `POST /api/upload/test`)에
  `dry_run=true`로 먼저 태워 파싱 오류 없이 예상 행 수만큼 반영되는지 확인 후 사용자에게 전달
  (실제 반영은 사용자 확인 후 별도 진행).

## 알아두면 좋은 점 (사용자에게 함께 안내)

- 이 컴퓨터의 `ChargeProgramSpec` 테이블이 비어 있어(원본 충전 프로그램 엑셀 없음),
  `charge_program_deviation_pct`는 이 더미 데이터를 반영해도 전부 NULL로 남는다 — 1단 회귀
  X셋(`charge_program_deviation_pct` 포함)이 이 값을 요구하므로, 실제 회귀를 돌리려면
  `POST /api/charge-program/upload`로 원본 충전 프로그램 파일을 별도로 먼저 올려야 한다.
  이번 작업 범위 밖(원본 파일 자체가 없어 대신 만들어줄 수 없음).

## 추가 작업(같은 날, 후속) — 충전 프로그램 스펙 더미 생성

위 문제(회귀가 "유효 표본 0건"으로 실패)가 실제로 발생하는 것을 사용자가 화면에서 확인한 뒤,
근본 원인(원본 충전 프로그램 파일 부재)까지 더미로 해소해 달라는 요청을 받아 추가함.

- `scripts/generate_charge_program_spec_dummy.py` 신규 — `backend/etl/charge_program.py`가
  파싱하는 것과 동일한 구조(정격용량별 시트 + 바이어별 블록 + STEP/Total 행)로 위 37개 조합
  전부에 대응하는 충전 STEP 기준표 더미(`충전바이어_더미_충전프로그램.xlsx`)를 생성.
- Total 충전량[Ah]은 조합마다 108~116% 사이에서 해시 기반으로 결정적으로 다르게 설정 —
  처음에는 전 조합에 동일한 112%를 썼다가 `charge_program_deviation_pct`가
  `charge_ratio`의 완전한 선형 변환이 돼(정격용량이 분자·분모에서 약분됨) VIF가 9999로
  캡되는 완전 다중공선성을 실제로 재현·확인함 — 회귀 자체는 여전히 성공하지만(캡 처리
  덕분) 이 컬럼이 독자적인 정보를 전혀 못 주는 더미 데이터 품질 문제였음. 조합별로 흩어
  잡은 뒤 VIF가 7.8 수준으로 낮아지고 두 컬럼이 여전히 강하게 상관되면서도 완전히
  겹치지는 않는 것을 재검증함.
- 임시 scratch DB(포트 8001, 실제 데모 DB는 건드리지 않음)에 process/test/charge-program
  더미 3개를 순서대로 실제 업로드해 `charge_program_deviation_pct` NULL 0건, 4개 회귀
  엔드포인트(x-to-y/xy-to-z/x-to-z-baseline/xy-to-sae-cca/xy-to-en-cca) 전부 200 OK로
  확인 후 scratch DB 삭제.
- **프런트엔드에 충전 프로그램 업로드 UI가 없음**(`frontend/app`·`frontend/lib` 전체에
  "charge-program" 참조 0건, 확인됨) — `POST /api/charge-program/upload`는 API로만
  존재하고 `/upload` 화면 버튼에 연결돼 있지 않다. 이번 요청 범위 밖이라 UI를 새로 만들지는
  않았고, 사용자에게 curl 명령으로 직접 반영하는 방법을 안내함.
