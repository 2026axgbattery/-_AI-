## 2. 항목별 근거 대조 (표 → docs/prd.md)

### 2.1 과제내용
표의 "공정 데이터 입력만으로 포화도 예측 + SPEC 판정·원인진단 자동화"는 `docs/prd.md` §1(문제정의)의 세 가지 고통 중 세 번째("시험 전 로트는 깜깜이다")를 X→Y→Z 2단 캐스케이드로 해소한다는 §1 핵심 가설과 정확히 일치한다. 다만 표 문구는 캐스케이드의 최종 단계인 "Z(20시간 용량)"를 명시하지 않는데, 실제 범위는 Y뿐 아니라 §6 ③-2/④-2/⑤에 정의된 대로 **Z(20시간 용량)까지 포함**한다 — 표 문구가 과제를 축약해서 표현한 것일 뿐, 범위 축소가 아니다.

### 2.2 배포 환경 — "단일 프로세스, 창원공장 폐쇄망 내 로컬 실행 · Streamlit" (→ 피벗 후: Next.js+FastAPI)
- **단일 프로세스·로컬 실행**: `docs/prd.md` §3 Non-goals의 "다중 동시 편집을 위한 서버 인프라 구축 (별도 배포 서버 없이 로컬 PC 웹앱)"과 정확히 일치. Next.js(프런트)+FastAPI(백엔드) 두 프로세스로 구성되지만 둘 다 로컬 PC 한 대에서만 실행되므로 이 원칙은 그대로 유지된다.
- **폐쇄망**: `docs/prd.md` §3 Non-goals "외부 클라우드 API/LLM 연동(사외반출 금지 데이터이므로 전 구간 로컬 처리만 허용)", §8 "사외반출 금지 데이터를 외부 API/클라우드로 전송 시도" 행과 일치. 애플리케이션 레벨에서 외부 네트워크 호출 자체를 두지 않는다(`CLAUDE.md`).
- **Streamlit → Next.js+FastAPI**: 표는 피벗 이전 시점의 기록이라 "Streamlit"으로 남아 있다. **2026-09-10 사용자 결정으로 3일 MVP부터 Next.js(화면)+FastAPI(분석 엔진, `127.0.0.1` 전용)로 시작**한다 — 원래 v2에서 하려던 전환을 MVP로 앞당긴 것뿐, 새 기술을 추가한 것은 아니다(`.docs/02_nextjs-fastapi-구현-아키텍처.md` 참조). SQLite는 표대로 유지.

### 2.3 라이브러리 — "pandas, numpy, scikit-learn"
표에는 `scipy`가 빠져 있지만, `docs/correlation-reliability-review.md`가 이미 `scipy.stats.pearsonr`로 p-value를 계산하는 방법론을 확정했고 `docs/prd.md` §10-17("회귀결과에 통계적 유의성 표시 여부")도 이를 전제로 하므로, **`scipy`를 라이브러리 스택에 포함**한다(표 누락을 보정). VIF 계산(§6-③-1)에도 `statsmodels`(또는 `scikit-learn` 대체 구현)이 필요하므로 함께 명시한다.

| 라이브러리 | 용도 | 근거 |
|---|---|---|
| `pandas` | CSV 업로드·병합·lot_id 조인·집계(일/월/연 추이) | docs/prd.md §6-①, §6-③-4 |
| `numpy` | 파생값 계산(잔존율, 무차원화 비율 등) | docs/prd.md §7 LotDerived |
| `scikit-learn` | 1단(X→Y)·2단(X+Y→Z)·베이스라인(X→Z) 다중선형회귀 | docs/prd.md §6-③-1/③-2 |
| `scipy` | 피어슨 r + p-value 유의성 검정 | docs/correlation-reliability-review.md, docs/prd.md §10-17 |
| `statsmodels` (또는 동등 구현) | VIF(분산팽창계수) 산출 | docs/prd.md §6-③-1 |
| `fastapi` + `uvicorn` | 위 분석 함수를 API 엔드포인트로 노출(로컬호스트 전용) | `.docs/02_nextjs-fastapi-구현-아키텍처.md` (피벗 결정, §5-③ 대체) |
| `next`(Next.js, React, TypeScript) | 5화면 UI — `streamlit`을 대체 | `.docs/02_nextjs-fastapi-구현-아키텍처.md` |

### 2.4 DBMS — "SQLite"
`docs/prd.md` §7 데이터 모델 스케치(Lot/ProcessData/TestData/ConstantsByModel/LotDerived/AnalysisRun/Prediction/SpecJudgment/CauseDiagnosis 9개 테이블)와 `.docs/03_sqlite-스키마-설계.md`의 실제 DDL로 이미 구체화되어 있다. `docs/prd.md` §7의 append-only 원칙, §9 "이력 축적"(AnalysisRun 누락 없이 기록)이 SQLite 파일 하나로 충분히 달성 가능한 규모(100~수천 행)라는 것도 확인됨.

### 2.5 MVP — "업로드·입력·상관분석·예측·SPEC판정·이력저장 5화면 더미 동작"
`docs/prd.md` §5 "MVP (3일 집체, Next.js + FastAPI)" 행(2026-09-10 피벗 반영)과 §6 ①~⑤ 상세 요구사항에 1:1 대응한다:

| 표의 MVP 항목 | docs/prd.md 대응 | 화면(`.docs/02_nextjs-fastapi-구현-아키텍처.md`) |
|---|---|---|
| 업로드+입력 | ① CSV 업로드(파일 선택+드래그앤드롭) + lot_id 자동 매칭 + ② 수기입력(그룹 일괄 입력만 노출) — 2026-09-10부터 한 화면으로 통합 | `frontend/app/upload/page.tsx` → `POST /api/upload`, `/api/manual-fields/groups`, `/api/manual-fields/batch` |
| 상관분석 | ③-1/③-2 X→Y, X+Y→Z 회귀 + 베이스라인, ③-3/③-4 형명별 상세·추이 | `frontend/app/dashboard`, `frontend/app/detail-analysis` |
| 예측 | ④-1/④-2 미매칭 로트 Y·Z 일괄 예측 + 수동 시뮬레이션 | `frontend/app/prediction/page.tsx` → `/api/predict/y`, `/api/predict/z` |
| SPEC판정 | ⑤ Y·Z SPEC 판정 + 원인진단 | `frontend/app/dashboard` → `POST /api/diagnosis` |
| 이력저장 | `AnalysisRun`/`Prediction`/`SpecJudgment`/`CauseDiagnosis` SQLite 누적 저장 | `backend/db/repository.py` |

"5화면"이라는 표 표기와 실제 `output/*.html` 파일 5개(01/02/03/04/analysis_dashboard)가 정확히 일치한다.

### 2.6 최종 결과물 — "train/test 검증(R²/RMSE), 재학습 파이프라인, 실데이터 검증, 사내 배포"
**중요**: 이 4개 항목은 표에서 "MVP"와 구분된 "최종 결과물" 칸에 있는데, `docs/prd.md`에서는 이 4개 모두 **3일 MVP의 Non-goals(§3)이자 v2/이후 단계(§5)로 명시적으로 이관된 항목**이다. 즉 표의 "최종 결과물"은 3일 집체 산출물이 아니라 **과제 전체(3일 이후 v2 포함)의 도착점**을 가리키는 것으로 해석해야 정합적이다.

| 표의 최종 결과물 | docs/prd.md 대응 위치 | 비고 |
|---|---|---|
| train/test 검증(R²/RMSE) | §3 Non-goals "예측 모델의 학습/검증(train/val) 분리 및 R²·RMSE 등 성능지표 정식 검증", §5 v2 "학습/검증 데이터 분리 및 R²·RMSE 정식 검증" | 3일 MVP는 §9 성공지표에서 "파이프라인 완결성"만 확인, 정확도 지표는 의도적 제외 |
| 재학습 파이프라인 | §3 Non-goals "재학습(retraining) 파이프라인 정식화", §5 v2 "재학습 파이프라인" | MVP는 `AnalysisRun.is_latest_for_stage`로 이력만 관리, 자동 재학습 트리거는 v2 |
| 실데이터 검증 | §3 Non-goals "실제 운영 데이터로의 최종 교체 검증", §5 v2 "실제 운영 데이터 최종 교체·검증" | 3일 MVP는 더미 데이터(`process_data.csv`/`test_data.csv`) 기준 |
| 사내 배포 | §5 "이후 단계" "사내망 공유 배포(다중 사용자 동시 접속)" | 3일 MVP는 로컬 PC 단일 실행(§3 Non-goals), 사내 배포는 그 다음 단계 |

**결론**: 표의 "최종 결과물"란은 3일 뒤가 아니라 **v2~이후 단계까지 포함한 과제 전체의 목표**로 이해해야 하며, 이렇게 해석해야만 `docs/prd.md`의 3일 MVP 범위 정의와 모순되지 않는다. 3일 집체가 끝나는 시점의 완료 기준은 이 4개가 아니라 `docs/prd.md` §9 성공 지표(파이프라인 완결성, 예측 커버리지 100%, 캐스케이드 구조 완결성, 이상 로트 탐지, 재현성, 이력 축적)다.

## 3. 단계별 기술 스택 로드맵 (표의 "최종 결과물"에 도달하는 경로) — 2026-09-10 피벗 반영

| 단계 | 배포 환경 | 라이브러리/DBMS | 산출물 |
|---|---|---|---|
| **1단계 — 3일 MVP (피벗 후)** | 단일 프로세스 구성 원칙 유지, 창원공장 폐쇄망 내 로컬 실행 · **Next.js(화면) + FastAPI(분석 엔진, `127.0.0.1` 전용)** | pandas/numpy/scikit-learn/scipy/statsmodels(FastAPI 뒤) + SQLite | 표의 "MVP" 5화면 더미 동작, **`docs/design.md` 픽셀 단위 구현 포함**(`docs/prd.md` §9 성공 지표 충족) |
| **2단계 — v2(10월 여유 범위)** | 동일 폐쇄망, 동일 Next.js+FastAPI 스택(전환 작업 없음 — 이미 1단계에서 사용 중) | 동일 분석 라이브러리 + 동일 SQLite | train/test 검증(R²/RMSE), 재학습 파이프라인, 캐스케이드 vs 베이스라인 정량 비교, `saturation_calc` 활성화(확보 시) |
| **3단계 — 이후 단계** | 사내망 공유 배포(다중 사용자 동시 접속), 역할 기반 접근 제어 | 동일 스택 + 동시접속 대응(§8 "SQLite 파일 동시 접근" — 쓰기는 FastAPI 프로세스만, 열람자는 읽기 전용) | 실 데이터 최종 교체·검증, 사내 배포, 이상 사전예측 솔루션 확장 |

**피벗으로 사라진 것**: 기존에는 1단계(Streamlit)→2단계(Next.js+FastAPI) 사이에 프레임워크 전환 작업이 있었지만, 이제 1단계부터 2단계까지 **스택 전환이 없다** — v2는 순수하게 기능 확장(학습/검증 분리, 재학습, saturation_calc)만 하면 된다. 다만 이는 **3일 안에 Next.js+FastAPI 초기 셋업까지 끝내야 하는 부담**과 맞바꾼 것이므로, `history/phase/phase_01_plan.md`의 Day1 계획에 이 리스크를 명시해 뒀다.

이 로드맵은 `docs/prd.md` §5(기능 목록 MVP/v2/이후 단계 표)·§3(Non-goals)·`CLAUDE.md`(기술 스택)·`AX전문가과정_..._v2.docx` 부록 C(기술 스택 로드맵, 피벗 반영 완료)에 있는 결정을 표의 "최종 결과물" 칸과 연결해 재구성한 것이다.
