# 23. 튜터 조언 정리 및 v2(10월) 방향성

## 배경

원본 메모(`튜터 조언.txt`, 저장소 루트)는 AX 전문가과정 튜터링 세션에서 받은 조언을 속기로 남긴 것이다.
문장이 축약·생략된 부분이 많아 이 문서에서 맥락을 살려 정리하고, 이 프로젝트(전지 포화도/CCA 예측
웹앱)의 v2(10월) 범위와 어떻게 연결되는지 정리한다. 원문 자체는 참고용으로 루트에 남겨둔다.

## 핵심 조언 (주제별 정리)

### 1. 검증이 최우선 — 새 기능 확장보다 먼저
- 새로운 기능(모델/파이프라인)을 넓히기 전에 "지금 있는 것이 맞는지" 검증부터 한다.
- 병목(bottleneck)이 있을 수 있다는 전제로, 당장 테스트할 수 없으면 **버전을 나눠서 관리**한다 —
  예를 들어 실측 데이터가 준비되기까지 시간이 걸린다면, 지금 확보한 데이터로 "버전 A"를 확정해 두고
  대기 기간이 끝나면 다음 버전으로 넘어가는 식으로 진행한다(→ "데이터가 한 달 뒤에 나온다면?"과 같은
  상황을 미리 대비).
- 데이터 수량 자체가 "통계적으로 신뢰 가능한 수량"인지 먼저 확인해야 한다.

### 2. 성공/실패 기준을 먼저 명문화
- "예측이 몇 번 맞아야 정확한 시스템으로 볼 것인가"에 대한 **정량 기준**이 있어야 한다.
- **실험(도메인) 성공 기준**과 **시스템(소프트웨어) 성공 기준**은 별개로 정의한다 — 사람이 검증한
  정답(모범 답안)과 시스템이 낸 결과를 비교하는 축.
- 파이썬 기반 **테스트/채점 모듈**을 별도로 만들어서 기준 충족 여부를 자동으로 확인한다.
- **실패 기준**도 마찬가지로 명확해야 하고, 실패했을 때 "다시 자동으로 돌릴지" "사람이 검토하게 할지"
  까지 프로세스로 정해둬야 한다.

### 3. 결과 검증 방법론
- 사람이 먼저 "모범 답안"(정답 세트)을 만들고, 검증 가능한 범위로 스코프를 좁혀서 진행한다.
- 표준화 단계에서 AI 쪽에서는 **온톨로지 기법**(관계 기반 계층 분류)을 활용한다 — 데이터 범위와
  하위 항목의 소속 관계를 정리해두면 데이터를 찾아가기 쉬워진다. 사람이 상위 그룹화를 미리 해주면
  AI가 이해하기 더 쉬워진다.

### 4. 시스템 일관성(재현성) 원칙
- 시스템은 **입력이 같으면 항상 같은 결과**를 내야 한다(대량 데이터에서도 마찬가지).
- 성공 케이스는 대시보드에 반영하고, 실패 케이스는 재실행하거나 별도 표시로 구분한다.
- "실험 성공 케이스"와 "시스템 성공 케이스"를 구분해서 관리한다.

### 5. 데모 버전과 테스트 버전 분리
- **"보여줄 버전"(데모/발표용)과 "테스트 버전"(내부 검증용)을 나눠서 관리**한다.
- 테스트 가능한 버전을 별도로 만들어 거기서 먼저 검증하고, 검증이 끝나면 보여줄 버전에 반영한다.
- 웹은 배포 즉시 최신 버전을 바로 볼 수 있지만 앱(네이티브)은 재다운로드가 필요하다는 차이도 언급됨.

### 6. 발표 준비
- 최종 산출물은 PPT + 영상.
- 튜터가 공유하는 "스킬"(정해진 포맷)이 있으면 그 포맷을 그대로 따라 작성한다 — Claude/GPT에 스킬
  폴더를 전달하면 정해진 포맷대로 결과물을 만들어 줄 수 있다(예시 파일 필요).

### 7. (규모를 키울 경우) 문서·폴더 구조 확장 전략
- 문서와 폴더를 늘려서 서로 다른 프로젝트를 폴더 단위로 분리하고, 하나의 대시보드에서 여러 프로젝트를
  한눈에 보이게 구성하는 방식도 고려할 수 있다(예: 검사/분석 등 역할별로 분할).
- 상호 의존성이 있는 작업은 "핸드오프" 형태로 다른 프로젝트(폴더)에 넘기는 구조.
- 정교한 작업이 필요할 때는 PRD 하나로 퉁치지 말고 **상세 기능 명세서**를 별도로 만들어 기능 단위로
  역할을 쪼개는 게 좋다 — 폴더를 상세기능명세서/PRD/ERD/요구사항으로 나눠 관리하는 방식.

## 10월 실행 순서 (원문 메모 기준)
1. 합격선(패스 기준) 받기
2. 실제 데이터를 1개월간 반영
3. 채점 및 이상 여부 확인
4. 재학습 규칙 정하기
5. 학습 데이터 최적화 — 모델별로 BEST/실패 사례를 넣어보고 채택 여부 결정

## 이 프로젝트에 연결되는 지점

| 튜터 조언 | 이 프로젝트의 현재 상태 | 연결 지점 |
|---|---|---|
| 성공/실패 기준 명문화 + 파이썬 채점 모듈 | `docs/prd.md` §9 성공지표는 있으나 "몇 번 맞아야 정확한가"의 정량 임계값은 없음. R²/RMSE 정식 검증 자체가 §3 Non-goal(v2)로 미뤄져 있음 | v2 착수 시 제일 먼저 할 일로 삼을 것 |
| 데이터 수량 신뢰성 확인 | 형명별 표본 중앙값 2~3건, `MIN_SAMPLE_SIZE_FOR_MODEL_DETAIL=5`(코드 기본값)가 미확정 | `.docs/22` "16번" 항목과 동일 건 |
| 데모 버전/테스트 버전 분리 | 현재는 단일 버전(로컬 SQLite `backend/db/app.db` 하나만 존재) | v2에서 검증 전용 DB/브랜치를 따로 둘지 검토 필요 |
| 실패 시 처리 프로세스(재실행 vs 사람 검토) | `InsufficientSampleError` 같은 "정상적인 데이터 부족" 상태는 이미 구분돼 있으나, "예측값이 SPEC과 다르게 틀렸을 때" 재학습·사람 검토 프로세스는 아직 없음 | §3 "재학습 파이프라인 정식화" Non-goal과 직결 |
| 온톨로지 기법으로 데이터 표준화 | 아직 미적용 | 형명(35개)·용량군(6개) 계층 구조를 명시적으로 태깅하는 것부터 검토 가능 |
| 발표(PPT+영상), 스킬 포맷 | `reports/`에 PPT 생성 코드(python-pptx) 있음, 영상은 아직 없음 | 튜터가 공유하는 스킬 포맷을 받으면 반영 |

## 확인이 필요한 부분 (원문이 불명확함)

아래는 원문 메모에서 문장이 끊기거나 축약돼 정확한 의도를 확정할 수 없었던 부분이다. 세션 내용을
더 기억하고 있다면 보완이 필요하다 — 추측으로 채우지 않고 원문 그대로 남겨둔다.
- "예측 및 채점 점수 및 두 ㄱ" — 뒷부분이 잘린 것으로 보임.
- "토론에 대한 비용 절감" — 어떤 토론/논의를 줄인다는 것인지 맥락 불명.
- "시스템에 성공 케이스가 1만개가 나온다,? 나머지는 실패케이스가 된다" — 대량 데이터에서 일관성을
  어떻게 측정할지에 대한 예시로 추정되나 정확한 기준식은 불명확.
